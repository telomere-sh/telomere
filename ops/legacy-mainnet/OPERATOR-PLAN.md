## Isolation and resources

1. A separate root daemon is mandatory. Legacy `cleanupOrphans()` deletes all matching `telomere.managed=true` containers in the selected daemon, without chain/deployment scope. Its socket must be `/run/telomere-mainnet-docker/docker.sock`, its data root `/opt/telomere-mainnet-pilot/docker-data`, exec root under `/run/telomere-mainnet-docker/exec`, and containerd namespaces `telomere-mainnet-cpu` and `telomere-mainnet-plugins`. Do not point it at the staging socket or namespace. The actual Docker29.8.1 installation automatically selects shared `/run/containerd/containerd.sock` even when no socket is specified. Separate namespaces are therefore essential; this is not a separately running containerd process. Separate Docker roots and containerd namespaces do not isolate the host network namespace.
2. CPU Cells always receive `--network=none`. The daemon must use the explicitly owned `tlmr-mainnet0` bridge with manually assigned `172.31.254.1/24`, MTU1500, and `fixed-cidr=172.31.254.0/24`. Do not use `bridge=none`, `bip`, or `default-address-pools`; the exact installed Moby daemon can delete the global legacy `docker0` during startup for `bridge=none` and for some address-pool settings. A custom user-managed bridge cannot combine with `bip`; dockerd `--validate` does not catch that runtime rejection. Keep iptables, ip6tables, ip-forward and ip-masq false. The proposed default runtime is existing `/opt/telomere-host-runtime/gvisor/runsc`. Root must validate daemon config and a fixed-task container before controller activation. Do not relax the reviewed isolation merely to make an acceptance pass.
3. Root reports no native PostgreSQL binaries. Use one trusted PostgreSQL container in the new daemon with explicit `--runtime=runc --network=host`, PostgreSQL `listen_addresses=127.0.0.1`, port `15435`, separate role/database `telomere_mainnet`, a new random database password and a dedicated data directory/volume. Do not connect this database to staging. Host networking is for this trusted DB container only; CPU Cells always receive `--network=none`.
4. Reviewed local cached pins supplied by root: CPU `node@sha256:0a7108bf6c7bf5de370ffb1a3ed6be93d405b43ff159f681a8d18c0e2bc2e402`; PostgreSQL `postgres@sha256:721873c34ceb9f8d8fc265984940dc982404c105f19ad51be9fdc5970a6080ea`. Saving from the existing daemon and loading into the new daemon must not stop, retag or replace existing resources. These pins still need local manifest/image verification in the new daemon.
5. Mainnet bind is `127.0.0.1:3282` only. SSH preview uses local `3282 -> VPS127.0.0.1:3282`; keep `PUBLIC_ORIGIN=http://127.0.0.1:3282` until a reviewed HTTPS origin is chosen. Do not expose a public listener or change DNS/firewall for this preparation. A future origin change invalidates the reviewed private profile hash and authentication messages.
6. Separate controller state `/opt/telomere-mainnet-pilot/data/controller` and ciphertext directory `/opt/telomere-mainnet-pilot/data/cysts`, each `0700` owned `995:993`. Local ciphertext is private storage, not independent regional replication. Do not copy old financial rows; `bindControllerChain()` rejects an unbound populated public DB or mismatched chain binding.

## Incident correction and owned bridge persistence

The first draft incorrectly used `bridge=none` and claimed a private containerd child. At18:01:49UTC on15October2026 root started that separate daemon; at18:01:50 the existing default bridge was removed and the old PostgreSQL veth lost its bridge. Read-only source inspection of installed Moby commit464cd50 confirms `configureNetworking()` calls `removeDefaultBridgeInterface()` for disabled bridging; that function deletes the host-global `docker0`. The default daemon, old database container, and Enclave bridge stayed running, but the old staging controller lost PostgreSQL connectivity. This is an actual preparation incident, not a hypothetical risk.

Root stopped only the new daemon/database, recreated `docker0` with its verified172.17.0.1/16/MTU1500 settings, and attached only the verified old PostgreSQL veth. Network probes then passed. PostgreSQL retained the disconnected old session's advisory lock; read-only diagnosis identified exact backendPID1600, backend_start05:02:59.827278UTC, client172.17.0.1:51318 and lock(classid0,objid728419023,objsubid1). Root conditionally terminated only that proven stale backend, after which staging recovered. Do not kill additional sessions or restart the shared default daemon as part of this correction.

The corrected `prepare-network.py` draft verifies the exact root-owned bootstrap marker before doing anything. It creates only its fixed bridge when absent and the subnet is unused; it never alters a pre-existing bridge, deletes a link, moves a veth or changes firewall rules. An existing bridge must already have the exact kind, address, MTU, UP flag and ownership alias `telomere-mainnet-prepare-20261015:f1f1fa857fb34ae9adb708ecf6af7166`; root must deliberately add that alias to the bridge root manually created before installing this guard. A partially created or mismatched bridge is a refusal requiring operator review.

Install the root-owned guard at `/opt/telomere-mainnet-pilot/operator/prepare-network.py` and the draft network unit as `/etc/systemd/system/telomere-mainnet-network.service`, after review. The Docker unit requires the oneshot network unit. The oneshot has no stop action. Each Docker start/restart also invokes the guard before and after dockerd: it snapshots all pre-existing other interfaces, including docker0/address/index/MAC/MTU/master/flags, into root-only `/run/telomere-mainnet-docker/legacy-network-before.json`, and then requires exact preservation. It refuses to start when the legacy172.17.0.1/16 bridge is absent. Do not bypass a refused guard with a generic network reset. Also verify old staging health, Anvil, Enclave PostgreSQL and Redis before and after every daemon restart; interface snapshots do not prove application health.

The updated preflight requires four new independently reviewed fields in private expected.json: `dockerConfigurationSha256`, `networkGuardSha256`, `networkUnitSha256`, and `dockerUnitSha256`. These hash the exact installed private daemon JSON, operator guard and both systemd units. It also validates every daemon JSON option against the corrected explicit-bridge configuration, rejecting missing/additional options, shared namespaces/socket/data paths and the known-dangerous bridge/address-pool variants. The installed Moby29.8.1 build has inconsistent JSON/flag handling for the plugin namespace: the plural JSON spelling was ignored, while daemon validation rejects the singular spelling. Both plugin namespace JSON keys are therefore absent and rejected by fixtures. The dedicated daemon unit supplies `--containerd-plugins-namespace=telomere-mainnet-plugins` explicitly on ExecStart; root must first verify acceptance of this exact flag with the installed binary and final JSON. The independently pinned Docker unit hash binds that CLI option. After the one reviewed dedicated-daemon restart, verify actual Docker info/API namespace values: Containers=`telomere-mainnet-cpu`, Plugins=`telomere-mainnet-plugins`; a configuration-file check alone is insufficient. Re-run configuration-only after installing these reviewed files and updating expected.json. Keep activation absent and the controller inactive throughout.

## Disabled controller and pre-sign verification

The units are drafts with no `[Install]` section. Do not enable or start the controller, run `main.ts`, run `npm run demo`, invoke the staging bootstrap, or run the broadcast script. `startPilot()` performs recovery and starts its worker automatically; there is no worker-off environment switch. Its `ChainBridge.check()` requires an actually deployed matching escrow even before DB opening.

Keep `private/activation.json` absent. The controller draft also has a `ConditionPathExists` guard and a root-only `ExecStartPre=+... preflight.mjs --verify-activation`. The read-only `preflight.mjs --configuration-only` draft checks the exact eight-field bootstrap ownership marker, bounded private profile, source/runtime hashes, new identity, private state directories, isolated Docker target/configuration and public-chain config. It also binds the exact private unsigned-plan file SHA-256, recomputed review digest, creation-code hash, nonce, CREATE address and constructor roles. Syntax validation and local public-data fixture tests exercise the pure validation helpers. Root reports the preceding guard version passed configuration-only on the VPS with906 runtime pins; the revised network/hash checks need installation and a new run by root.

The current watchdog CLI accepts only `demo` and `testnet` for `--expected-mode`; do not install/copy/enable the staging watchdog for mainnet. ## Wallet boundary and later activation

Prepare only unsigned deployment bytes using `scripts/deploy-contracts.ts --network base-mainnet --public-profile=<new reviewed profile>`. It checks canonical USDC pins, EOA deployer nonce and exact constructor roles. Preserve the review digest and gas estimate, including any estimate that used a read-only balance override. An estimate does not credit the wallet. The owner must review and sign deployment in their own wallet. Do not invoke `submit-deployment.ts`: that command imports a deployer key and broadcasts after its explicit gate, outside this preparation.

After the owner's deployment transaction, a separate review must verify canonical receipt, contract address, runtime bytes/source and immutable token/quoteSigner/receiptSigner/treasury. Root may then create a root-only activation record binding those values, the reviewed plan digest, exact source commit and profile hash. The activation guard requires the exact owner's CREATE input/from/value/nonce from `getTransaction`, successful canonical receipt, and finalized head covering the deployment block. It compares 12,573 deployed runtime bytes at both the receipt and current canonical block against independently simulated expected keccak `0xd2ce03e0de4dc334d671294ae5f900eee12ff05cebc6f6484455103f0b204ed5`, rather than trusting a hash supplied only by the activation record. The activation record field is `escrowRuntimeKeccak256`. The draft only observes records and RPC state; it never broadcasts. Native USDC proxy hash, implementation address/hash and metadata must be rechecked from a canonical Base block; don't substitute a token label or old sample hashes.

The operator relay needs Base ETH for future settlement gas; USDC belongs to the payer's deposit/budget, and the contract has no collateral requirement. Do not fund either automatically. Before opening the pilot, run actual funded deposit, Leash, open/stop, settlement/refund and restart acceptance under the owner's approved limits. Only then consider manual controller start and a separately reviewed monitoring service.
