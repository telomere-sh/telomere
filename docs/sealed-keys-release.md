# Sealed Cell Cyst key release boundary

The owner-side `src/sealed-keys/release.ts` module adds a **fail-closed key-release boundary** for the latest completed application Cyst checkpoint. It is not an attestation provider and does not turn the ordinary HostKit container into a TEE.

The owner selects the expected owner/agent/application schema, checkpoint ID and durable operation ID, run ID, host ID, Cell audience, reviewed TEE measurement, policy SHA-256 and recipient X25519 public key. Release first generates a new 256-bit challenge and the exact 64-byte `report_data` expected in the Cell quote, then invokes a trusted `SealedCellEvidenceCollector` to request raw evidence from that Cell, and passes the result and the same challenge to a trusted `SealedCellHardwareVerifier`. The first 32 bytes of `report_data` are SHA-256 of the UTF-8 JSON array `['telomere.sealed-cell.report-data.v1', owner, agent, applicationSchema, checkpointId, operationId, runId, hostId, audience, teeMeasurement, policySha256, recipientPublicKey, challenge]`; the final 32 bytes are the raw challenge. The exact field order, lowercase hex encoding and version string are protocol constants. The verifier's hardware-verified verdict must return this authenticated `report_data` and bind every selected field. The verdict must be no more than 60 seconds old, may have no more than five seconds of clock skew, and must expire within 60 seconds of verification. Freshness is checked before and after reading the owner vault and immediately before returning the packet. Cancellation, missing or oversized evidence, unrecognized fields, stale or mismatched verdicts, absent or pending checkpoints, and tampered recovery records fail closed. This call order and expected-byte calculation do not themselves prove that evidence is fresh: the real verifier must authenticate the quote and extract its actual `report_data`.

Only after these checks does the module read the recovery key through the existing `CystCheckpointVault` exclusive journal. It verifies the completed checkpoint's metadata and authenticates the original ciphertext using `decryptCheckpoint`. The key is then encrypted for the quote-bound, non-exportable recipient X25519 key with HKDF-SHA256 and XChaCha20-Poly1305. AEAD additional data covers the full Cell context, attestation reference, challenge, ephemeral key, salt and nonce. The returned packet contains ciphertext and public context only. The loaded key, temporary key copy, derived secret and authentication plaintext are cleared from mutable buffers. The recipient helper checks the expected context and expiry before opening the packet. It must run inside the measured Cell, and the resulting key must remain there.

The `SealedCellHardwareVerifier` is a **trusted integration boundary**, not an evidence parser. A real adapter must verify Intel TDX quote signatures and collateral, accepted TCB/advisories, debug-disabled status, exact measurement and policy, nonce freshness, and compare the authenticated quote's 64-byte `report_data` to the requested bytes. The v2 sealed packet commits to that value in AEAD AAD and derives its wrapping key from a domain-separated SHA-256 digest of the full packet header. A GPU Cell additionally needs NVIDIA CC evidence and an explicit supported CPU/GPU binding story. The current NEAR inference verifier returns an attested provider signer and TLS session; it does not attest a Telomere Cell or bind this recipient key. Its session is therefore rejected by this release contract. A test fixture returning the expected verdict proves the release logic but is **not** hardware evidence. No real TDX Cell adapter is connected or accepted yet.

Integration requirements before production use:

1. Generate the non-exportable X25519 recipient key inside an approved measured Cell. Authenticate its quote-bound public key and the Cell instance to the owner; never accept a key supplied only in an HTTP request.
2. Implement and independently review the hardware verifier adapter. It must derive all verdict fields from authenticated quote/evidence and reviewed local policy, not echo caller-selected values. Pin its binary and policy hash, bound its runtime, and refuse expired/revoked collateral.
3. Deliver the encrypted packet to that exact Cell over an authenticated owner-to-Cell channel. The recipient must verify the packet's trusted origin or independently authenticate the downloaded original Cyst metadata and ciphertext; X25519 encryption alone does not authenticate the sender.
4. Wire checkpoint restore and lifecycle fencing to the running Cell and perform end-to-end tests on the actual TDX hardware and storage path. The current application Cyst limit remains 2 MiB, without filesystem/process/GPU snapshot migration.

Local validation: `npx vitest run tests/sealed-keys-release.test.ts` passes 25 tests, including a fixed cross-language `report_data` vector, all-selector mutation checks, challenge-before-evidence ordering, one-shot collection with no verifier retry, rejection of evidence replayed under a new challenge, wrong measurement/policy/audience/key, stale/expired verdicts, recovery-key clearing after a cancellation race, changed packet context, tampered ciphertext and NEAR-session rejection. These tests use a fixture verifier and make no hardware-attestation claim. The [M7 acceptance plan](sealed-cell-m7-acceptance-plan-2026-10-13.md) lists the missing hardware and production integration gates.
