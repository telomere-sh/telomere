# x402 v2 payment module

Current network target: Base 8453 / Base Sepolia 84532 with native USDC. Dated acceptance and linked JSON evidence retain their original network/source scope; see [migration record](base-usdc-migration-2026-10-14.md).

## Implemented and exercised locally

`src/payments` exports an EVM facilitator, durable payment service, SQL schema/migration, authenticated facilitator routes, and an HTTP402 resource route. All payment tests run against disposable loopback Anvil and PGlite. The project never creates a user wallet or sends public transactions for these tests.

| Mode | Actual payment primitive | Settlement behavior |
| --- | --- | --- |
| `exact` | EIP3009 `transferWithAuthorization`, EIP712 `TransferWithAuthorization` | Transfer exactly the authorized atomic token amount once. |
| `upto` | Actual upstream Permit2 `permitWitnessTransferFrom` through actual upstream `x402UptoPermit2Proxy.settle` | Transfer a resource-server-selected amount up to the signed maximum once; the witness binds recipient, facilitator and earliest valid time. |
| `upto`, amount `0` | Durable local challenge consumption | Success with amount `0`, empty transaction identifier, and no chain transaction. The still-live signature is not revoked onchain. |

This follows the [v2 core specification](https://github.com/x402-foundation/x402/blob/7f2b2f1f77fa5317615735e3378a6fad41cccb4e/specs/x402-specification-v2.md), [EVM exact scheme](https://github.com/x402-foundation/x402/blob/7f2b2f1f77fa5317615735e3378a6fad41cccb4e/specs/schemes/exact/scheme_exact_evm.md), [EVM upto scheme](https://github.com/x402-foundation/x402/blob/7f2b2f1f77fa5317615735e3378a6fad41cccb4e/specs/schemes/upto/scheme_upto_evm.md), and [HTTP v2 transport](https://github.com/x402-foundation/x402/blob/7f2b2f1f77fa5317615735e3378a6fad41cccb4e/specs/transports-v2/http.md). The reviewed upstream revision is pinned in the fixture manifest.

No custom `PaymentEscrow` is used or advertised as standard x402. These are direct token transfers, separate from Telomere's Leash/run escrow. Connecting incoming payments to escrow deposits, agent income, or provider budgets requires an explicit application integration and accounting policy.

## Explicit request-binding extension

The module advertises `telomere-request-binding` version 1. Every resource server challenge includes a random nonce, challenge UUID, and SHA-256 binding of the exact HTTP method, configured resource URL and body digest in `accepted.extra.telomere`. The EIP3009 signed nonce must equal the challenge nonce; the Permit2 signed uint256 nonce must represent the same number. An immutable database record binds that signed nonce to all issued terms and the resource. Unsigned resource metadata cannot substitute a different challenge, price, recipient, body or endpoint.

The signed EIP3009 and Permit2 structs remain the standard structs. This extension requires client nonce selection from the challenge; an SDK that independently generates its nonce needs a small adapter. This implementation does not claim unmodified-client compatibility. Permit2 decimal and hexadecimal wire nonces are accepted and normalized. Echoing the declared extension in `PaymentPayload.extensions` is optional.

Supported wire subset: v2, EVM CAIP2 networks, six-decimal ERC20, 65-byte EOA signatures, exact EIP3009, and upto Permit2 witness transfers. Contract wallets, ERC6492 deployment, ERC1271, compact signatures, exact Permit2, EIP2612-assisted approval, approval gas sponsorship, arbitrary extensions, batch-settlement and escrow payment flows are not advertised. Missing Permit2 allowance returns `PERMIT2_ALLOWANCE_REQUIRED`; the payer must approve Permit2 separately.

## Configuration and fail-closed pins

Construct `EvmPaymentChain(publicClient, dedicatedWalletClient, pins)` with the reviewed chain ID, token runtime hash, token kind, recipient, facilitator address and confirmation count. Exact additionally requires `reviewedEip3009: true` and the actual token's EIP712 name/version. Upto requires token name/version, actual Permit2/proxy addresses and runtime hashes. A token labeled `eip1967` requires the reviewed implementation address and runtime hash; both the implementation storage slot and implementation code are checked. The `immutable` label requires source review establishing that the token is not an upgradeable proxy. Native Circle USDC on Base uses `circle_proxy` with its own implementation slot, both code pins, canonical address and per-chain EIP-712 metadata. Other proxy designs remain unsupported.

Every enabled path checks chain ID, code pins, six decimals, domain separators and the exact proxy witness type. Verification checks balance, allowance, live authorization window, unused nonce, EOA signature and a read-only simulation of the complete authorized maximum. Before broadcasting persisted bytes, code pins are checked again. An unsupported token, changed implementation, missing contract, failed simulation or node failure prevents acceptance.

Outside disposable chain 31337, upto configuration requires canonical Permit2 `0x000000000022D473030F116dDEE9F6B43aC78BA3` and canonical x402 upto proxy `0x4020A4f3b7b90ccA423B9fabCc0CE57C6C240002`, plus independently reviewed deployed code hashes. The code does not assume that either contract exists on Base. Public Base profiles require native Circle USDC and exact reviewed EIP-3009 name/version, proxy and implementation pins. Their configuration does not by itself enable a deployed service. Permit2/proxy availability and code provenance still require separate review; generic local tests use disposable EIP-3009 and upstream Permit2/proxy fixtures.

## Durable settlement and resource execution

`X402PaymentService.initialize()` installs only the module's fixed SQL. `paymentSchema` and `paymentMigrationSQL` are exported for the controller's normal migrations. A database row lock coordinates independent service instances. Authorization identity is chain + scheme + token + payer + signed nonce. The challenge has a unique consumption constraint. Reusing an authorization with a different payload or actual amount returns an idempotency conflict.

Challenge issuance uses that same row lock and a durable count limit: 10,000 retained challenges by default, configurable from 1 through 10,000 with the constructor's fourth argument, `{ maximumChallenges }`. At capacity, only new issuance stops with `payment_challenge_capacity_reached`; existing verification, settlement and original-attempt recovery remain available. Expired and consumed rows still count, including after database restart. The module does not delete payment evidence automatically. Operators must plan a separately reviewed archive/retention policy before continuous public operation. See `payment-challenge-capacity-validation.json` for concurrency and disk-reopen acceptance.

`verify()` reads database/chain state and performs `eth_call`; it neither consumes the challenge nor writes a payment journal or sends transactions. `settle()` requires an authenticated resource server's actual amount and request hash. It commits raw signed transaction bytes, hash, sender nonce, authorization key and actual amount before the first network send. These raw bytes are private database data and are excluded from API responses.

A retry reuses the same bytes and hash. It does not construct a replacement transaction or choose a new sender nonce. A dedicated facilitator signer with an unresolved journal entry cannot sign another payment. An untracked pending nonce also blocks preparation. A nonce already present in any persisted attempt cannot be signed for a different authorization after a reorg; the original attempt must be reconciled first. Ambiguous sends and unavailable receipts retain `settlement_pending`, a nonempty transaction hash and network, with `success: false`. Canonical block hash, configured confirmation depth, exact token Transfer logs and consumed authorization nonce are required for success.

Every nonzero cached settlement, including success and revert, is inspected again against the original transaction before returning. This does not re-verify an expired or consumed payer authorization. An unavailable finality read returns `payment_finality_unavailable`, never the cached success. Lost confirmation depth or an orphaned receipt changes the original journal back to pending without broadcasting during that observation; a later explicit retry may resend only its original bytes. If another authorization already owns the signer reservation, the downgrade is refused with `payment_finality_reconciliation_required`. All observations, state changes and sends share the nonce reservation lock and reload the current journal, preventing stale observations from overwriting a subsequent reorg recovery. Configuration and journal-response consistency are checked even for chainless zero-charge entries. See `payment-finality-validation.json` for the actual reorg, restart, concurrency and RPC-outage evidence. Rechecking detects changes at observation time; it cannot promise that a chain will never reorganize after the response.

The HTTP resource route follows the authorization flow: verify, persist an execution intent, execute, persist the server-computed actual amount and result, settle, then expose the result. Completed execution and results are cached by challenge. Retries do not execute again. A crash after execution intent but before a durable result leaves `resource_reconciliation_required` and never triggers an automatic rerun. The resource executor receives a stable authorization-derived idempotency key for its own durable provider adapter. Resolving an uncertain provider result remains an operator action; there is no administrative endpoint that silently reruns or fabricates the result.

## HTTP integration surface

`createFacilitatorRoutes(service, authorizeSettlement)` exposes `GET /supported`, read-only `POST /verify`, and authenticated `POST /settle`. Both POST requests use the standard `{x402Version:2,paymentPayload,paymentRequirements}` body. At upto settlement, `paymentRequirements.amount` is the actual amount; `paymentPayload.accepted.amount` retains the signed maximum. A resource server authentication callback is mandatory; no default public settlement capability is provided.

`createPaidResourceRoutes(service,{url,scheme,maximum,execute})` emits `402` and base64 JSON `PAYMENT-REQUIRED`; reads `PAYMENT-SIGNATURE`; and emits `PAYMENT-RESPONSE` with the final or pending settlement status. The executor computes the actual amount. Public clients cannot select it. Pending payment returns `202` without the resource result. Fixed resource URLs disallow query strings for this adapter; request bodies and headers are bounded. Callers should add their normal authentication, rate limits and origin policy when mounting routes.

These exports are a separately tested module. Runtime mounting and funded Base enablement must be reported separately from local payment compatibility. Current local evidence is `tests/x402-payments.test.ts` and the upstream source/compiled artifact hashes in `tests/fixtures/x402-reference/provenance.json`.
