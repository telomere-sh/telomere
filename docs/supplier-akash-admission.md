# Akash supplier admission slice (M6)

Current network target: Base 8453 / Base Sepolia 84532 with native USDC. Dated acceptance and linked JSON evidence retain their original network/source scope; see [migration record](base-usdc-migration-2026-10-14.md).

This backend slice discovers a pre-approved Akash provider for an existing deployment order, reserves a conservative local treasury estimate, can submit **one operator-gated lease POST**, and reconciles the exact external lease identity. It also has a separately gated, single-attempt deployment DELETE for an active pinned lease. Lease creation requires both `policy.leaseCreationEnabled: true` and an `AkashLeaseWriteClient`; closure requires both `policy.deploymentCloseEnabled: true` and an `AkashDeploymentCloseClient`. Both switches default off. Neither writer nor the reservation service is mounted in the main controller. It does not create a deployment, sign a transaction, bill a Telomere run, or confirm a refund. `meterEligible` and `refundConfirmed` remain `false`; `billableSeconds` remains `0`.

The main controller can optionally mount a **read-only eligibility proof** at `GET /api/suppliers/akash/runs/{runId}/readiness`. Set `AKASH_READINESS_CONFIG` to an absolute path to a reviewed JSON file such as `{"version":1,"mode":"readiness_only","chainId":31337,"escrowAddress":"0x...","leaseCreationEnabled":false}` (use the deployed chain and escrow pins). The file must be a bounded regular, single-link file; on Unix it must not be accessible to group or others. This route requires the normal owner session, loads the owner's stored quote, reads the actual onchain escrow, rejects mismatched terms, and reports admission and runtime blockers. It makes no Console request, treasury claim, reservation, or lease POST. By default the route is absent. A profile that requests lease creation or adds fields is rejected at startup.

The current paid Cell escrow limits a run to **120 seconds**, while Akash Console requires a runtime limit in whole hours, so the minimum is **3,600 seconds**. `runtime_too_short` is therefore unavoidable for current Cell runs. An EVM USDC balance cannot stand in for current Console `uact` credits or an observed `uact`/USDC conversion. The controller intentionally has no trusted treasury callback or live activation wiring until these constraints are resolved; the read-only proof does not imply operational Akash capacity.

An optional [owner-signed supplier binding](supplier-akash-signed-binding.md) now checks the exact provider, deployment, runtime, price and projected USDC reserve against the original signed PlatformQuote during private planning. The signed mode blocks lease submission because Console cannot atomically enforce the signed bid price. It is unmounted and disabled by default; it does not change the 120-second runtime limit or prove supplier payment.

The adapter uses the documented Akash Console endpoints `GET /v1/providers/{address}`, `GET /v1/bids?dseq=...`, `GET /v1/deployments/{dseq}`, and `GET /v2/deployment-settings/{dseq}`. The optional writer uses [the current `POST /v1/leases` contract](https://akash.network/docs/api-documentation/console-api/api-reference/): it sends exactly one composite bid with `dseq`, `gseq`, `oseq`, and provider. The `manifest` request field is deprecated; Console sends its recorded SDL to the provider. The Console API [documents composite bid identity and per-block `uact` price](https://akash.network/docs/api-documentation/console-api/api-reference/) and [documents provider health and audit fields](https://akash.network/docs/api-documentation/rest-api/providers-api/). Console automatically funds deployments while credits remain, so a missing runtime limit is rejected. The settings GET may initialize a settings record on first read on the Console side; it does not create a deployment or lease.

`SupplierService.plan` accepts only a trusted internal call. It queries an authoritative `approvedRun` dependency and checks the EVM owner, run ID, active CPU admission, duration, and escrow ceiling before reading the provider market. It requires a Console deployment owned by the specified Akash account, no existing leases, a non-null runtime limit no longer than 24 hours **and no longer than the approved run**, an open `uact` bid, and a provider from the configured allowlist with audited/online/current-version status and at least 95% 30-day uptime. It chooses the cheapest eligible bid deterministically. The allowlist is empty by default at the integration boundary, so nothing can be admitted accidentally.

A trusted operator callback supplies fresh `uact` inventory and a direct `uact`-to-USDC conversion observation. These values are never accepted from the public request; the adapter does not assume that USDC trades at exactly one USD. Admission calculates a conservative **projection** using `bid uact/block × configured max blocks/hour × runtime hours`, then adds at most a 3% inventory buffer. Both the run ceiling (250 USDC maximum) and total configured treasury ceiling must cover the projection. This is not a mathematically enforced maximum on Akash spending: block cadence, token price, and Console automatic funding can change.

`SupplierService.activate` is for a private operator caller only. It requires a fresh authoritative run approval with `expiresAtMs` beyond the *entire* Console runtime limit plus a two-minute POST window, enough USDC budget, a fresh treasury observation that still fits the original reserve, live credit inventory, the original manifest hash and empty deployment, unchanged runtime settings, and the exact still-open bid from an approved healthy provider. It durably changes `planned` to `lease_submission_pending` **before** a single `POST /v1/leases`. The POST result must show the pinned owner, deployment hash, provider, order and price. A timeout, HTTP error, malformed response, or crash leaves the full reserve held in pending state; no automatic retry is allowed because the lease may have been created. Read-only `reconcile` can observe the exact lease and move the row to `active`, or retain pending if it is not yet visible. Operator recovery must inspect the Console account and chain before deciding on cleanup. This path does not produce a Telomere meter or revenue tick.

`SupplierService.requestClose` is another private operator operation. It requires a previously observed `active` row and a fresh Console GET showing the exact pinned lease, deployment hash, owner, price and runtime limit. It durably marks `closure_submission_pending` **before** one [documented deployment DELETE](https://akash.network/docs/api-documentation/console-api/api-reference/). A timeout, HTTP error, malformed response, or crash keeps that state and the full reserve; the service never retries DELETE automatically. While the lease remains active, reconciliation keeps closure pending. Once the pinned deployment or lease is observed closed, reconciliation moves to `closed_unsettled`, still holding the full reserve. The DELETE response reports only success of the close request. Akash says unused Console credits return once the chain settles; neither that response nor a closed status proves the final provider cost or a credited refund. The [authenticated deployment GET](https://akash.network/docs/api-documentation/console-api/api-reference/) exposes raw escrow `funds`, `deposits` and `transferred`, but this slice does not infer a final USDC amount from them or release treasury capacity without independent final-account evidence.

The local journal uses an exclusive lock and atomic rename. Each idempotency key, Telomere run, and Akash deployment is reserved at most once. Restarting the service reloads these commitments. Akash admission also requires the [shared Akash/Nosana reserve](supplier-shared-reserve.md), which serializes both journals and checks one combined projected USDC ceiling. A crash-held lock fails closed until an operator confirms the old writer has stopped. `reconcile` polls the exact deployment and runtime settings; a changed owner, manifest hash, provider, price, runtime limit, or missing active lease moves the reservation into sticky quarantine. A closed external lease becomes `closed_unsettled`, which still holds the full local reserve because the Console status alone does not prove final cost or refund. No revenue tick is produced without a separate authenticated in-cell heartbeat and Telomere meter evidence.

An internal operator can call `cancelPlanned(owner, reservationId)` only while a row remains `planned` and a fresh Console read still shows the pinned empty deployment and unchanged runtime settings. This serializes with this service's lease-submission state change under the Akash journal lock. It leaves a durable `canceled_unsubmitted` tombstone, preserving the original quote, run/deployment claim and idempotency result, but excludes that row from Akash inventory and the shared projected USDC ceiling. Public records distinguish the immutable original `reserved*` projection from the current `reserveHeld*` amount, which becomes zero. A pending POST, active or closed lease, and quarantined row cannot be canceled through this method; their full reserve stays held. Another Console credential holder could still create an external lease after the fresh empty-deployment read and before the local cancellation commits. Production release of this projection therefore requires exclusive operational control of the Console owner/account or an authoritative provider-side cancellation guarantee. This is release of a local pre-submission estimate, not a provider refund or Telomere escrow settlement. The operation is not mounted on a public route.

Validation: `tests/supplier-akash.test.ts` covers bid choice, idempotency, restart, stale inventory, budget and allowlist checks, duplicate-deployment/treasury oversubscription, safe pre-submission reserve release, active/closed observations, quarantine, and bounded read-only HTTP. `tests/supplier-akash-lease.test.ts` checks the exact POST body, pre-POST durable intent, one-way replay fence, expiry/bid/hash/price/credit gates, refusal to cancel a pending POST, uncertain outcomes, and later lease observation. `tests/supplier-akash-close.test.ts` checks the exact DELETE transport, durable closure intent before transmission, restart and retry fence, changed lease rejection, and continued reserve holding after an observed close. All mutation tests use fake transports. On 12 October 2026, a read-only request to a real Akash provider record through `AkashConsoleReader.providers` succeeded. There is still no authenticated deployment/lease/close acceptance because this workspace has no funded Akash Console account and no approved Telomere run for it; no paid POST or live DELETE was made.

Remaining M6 work: make a paid Cell capable of covering the entire bounded Akash runtime before wiring an authoritative `approvedRun` callback or live writer; move the journal to its PostgreSQL transaction boundary; provision a bounded funded Console account with a trusted `uact` credit/price observation, reviewed deployment SDL and account-exclusive close procedure; obtain authenticated provider status with certificate validation and in-cell heartbeat; reconcile final Akash cost and refund against treasury inventory and Telomere escrow; complete Nosana and Golem payment paths. This is a locally tested lease lifecycle path, not operational supplier capacity or production settlement.
