# Akash read-only escrow observation

Current network target: Base 8453 / Base Sepolia 84532 with native USDC. Dated acceptance and linked JSON evidence retain their original network/source scope; see [migration record](base-usdc-migration-2026-10-14.md).

`src/suppliers/akash-escrow-observation.ts` adds a private, read-only accounting aid for an existing Akash supplier reservation. `AkashConsoleEscrowObserver.observe(record, previous?)` makes exactly one authenticated, bounded `GET /v1/deployments/{dseq}` request. It validates the deployment owner, sequence and manifest hash against the durable supplier record, and validates the listed lease's provider, group/order and price. It also requires the escrow account's `scope: deployment` and exact `xid: owner/dseq`. This format follows the [Akash chain SDK's `DeploymentID.ToEscrowAccountID`](https://github.com/akash-network/chain-sdk/blob/go/v0.1.9/go/node/deployment/v1/escrow.go) and [`DeploymentID.String`](https://github.com/akash-network/chain-sdk/blob/go/v0.1.9/go/node/deployment/v1/deployment.go). An active deployment must still show its exact active lease. The transport accepts only the fixed Console origin and refuses redirects; failures return a credential-free error.

The observer parses the [Console deployment escrow fields](https://akash.network/docs/api-documentation/console-api/api-reference/) as exact decimal strings. It sums repeated `uact` entries and represents balances as **integer units of 10^-18 uact**. This preserves the fractional micro-units that can arise in chain settlement. A signed `funds` balance and an `overdrawn` escrow state are allowed, while cumulative `transferred` must be nonnegative. Unknown denominations, excess precision, changed identities and a decrease in either settlement height or cumulative transfer from a prior observation fail closed. Without a prior observation, `transferredDeltaUactAtoms` is `null`, because a cumulative transfer cannot be attributed to the current Telomere run. The Console reference describes `leases[]` as active leases; a closed deployment may return no lease row. In that case the observation says `leaseState: not_listed` and makes no provider/price confirmation from that GET. A prior pinned active observation and independent chain/provider evidence would be required for final reconciliation.

The output always says `settlementConfirmed: false` and `reserveReleaseEligible: false`. `transferred` is an observed Akash escrow field, not a Telomere meter tick, a final provider invoice, an account-credit refund, or a USDC conversion. The observer does not change the supplier ledger, release a reserve, submit a lease or close a deployment. It is not mounted in the controller. Akash [automatically funds deployments from Console credits](https://akash.network/docs/getting-started/how-funding-works/), so a deployment-level escrow balance is not an authoritative available account-credit balance. That separate observation, conversion source, final account-credit reconciliation and an accepted supplier meter remain M6 release work.

This accounting aid does not resolve the current **120-second Telomere Cell versus 3,600-second Akash minimum runtime** mismatch. A funded, bounded long-running escrow product must be designed and approved before a real Akash lease can be charged to a Telomere run. The tests use fake Console responses and verify exact decimals, identity checks, regression rejection, one bounded GET and credential redaction; no paid Console call was made.

## Minimum long-running supplier product before lease activation

The deployed public Platform runtime advertises and validates at most 120 seconds, even though the separate `PlatformRunEscrow` contract has a 7-day hard maximum. The legacy `TelomereRunEscrow` itself caps runs at 120 seconds. Neither contract maximum nor an hour-long Console setting makes a current paid Cell an accepted 3,600-second supplier run. Do not stretch the current quote, reuse a 120-second run across an hour-long lease, or map supplier activity onto a HostKit CPU meter.

1. Specify and review a **versioned supplier escrow/admission contract**. The owner deposits real Base USDC and authorizes an explicit supplier Leash. A signed quote must pin the Telomere run, owner, Akash owner, `dseq/gseq/oseq`, approved provider, manifest hash, maximum whole-hour duration, maximum USDC charge including fee, quote expiry and a bounded conversion policy. Opening atomically reserves the full owner ceiling and enforces per-run, per-hour and per-day limits. It must expose a permissionless full refund after a bounded timeout if settlement evidence never arrives. A supplier run must have its own receipt domain and accounting state; the existing HostRegistry and HostKit CPU receipt are not a substitute.
2. Add a distinct long-running runtime that admits **at least the full 3,600-second Console limit plus activation/close margin**. It must verify the owner-funded onchain reservation, approved provider, reviewed SDL and deployment settings immediately before the single journaled lease POST. It must persist the immutable Console identity and run-to-deployment binding in a transactional journal. Repeated or ambiguous POST/DELETE outcomes remain fenced; the operator must inspect the external account before any recovery action. Deployment `runtimeLimitHours` and account controls must be rechecked throughout the run. Console auto-funding cannot be disabled per deployment, so use a dedicated, bounded-credit Console account with no card auto-recharge and exclusive credential control for the pilot; a Console runtime limit alone is not a dollar-spend cap.
3. Define **rolling receipts and settlement** at a fixed interval no longer than one hour. Each receipt needs a non-overlapping interval, cumulative runtime, cumulative provider cost, original provider/deployment identity, source observation height, and a unique hash. The contract must reject duplicate or out-of-order receipts and enforce cumulative `charged <= reserved`. Publish immutable receipt roots and permit incremental USDC charges only for authenticated, reconciled cost increments. If the provider/Console cost feed or USDC conversion is unavailable, pause new charges and lease extensions; retain the unspent owner reserve and close the deployment. The presently implemented `transferred` observation is an input to reconciliation, not by itself a payable receipt.
4. On closure, reconcile the Akash chain escrow's final `transferred`, `funds` and deposit history with a **final Console account-credit debit/refund and a time-bound, auditable USD-to-USDC conversion**. A closed deployment, successful DELETE and `funds == 0` individually do not prove the owner's exact USDC charge or recovered Console credit. Record the independent source IDs and resulting exact integer USDC amount, cap it by the original owner authorization, charge only the unpaid difference, and return the remainder to the owner's onchain balance. If reconciliation cannot prove the amount, retain `closed_unsettled` and use the contract's bounded dispute/timeout refund path; never synthesize a provider cost from elapsed time.
5. Accept the design only after local/fork tests prove exact budget arithmetic and receipt replay protection, Linux restart/crash recovery around POST and DELETE, two-provider/account-isolation cases, provider loss before and after each interval, changed SDL/settings/price, unavailable or contradictory cost/FX feeds, final refund, guardian stop, and permissionless timeout refund. Then run a small **owner-funded** testnet lease with separate Akash credits, capture the real deployment/escrow/account-credit evidence, reconcile the final USDC amount, and obtain independent contract/security/operations review before enabling public admission.

This is an implementation contract for future M6 work. No long-running supplier escrow, rolling settlement, funded Console account or live cost/refund proof is present in this slice.

## Why the existing Platform escrow cannot supply `ApprovedSupplierRun` yet

An `ApprovedSupplierRun` callback is a spending authorization, not merely evidence that some onchain run has a large `maxSeconds` and `ceiling`. The current `PlatformRunEscrow` can hold a run for up to seven days and its `getRun` exposes payer, host ID, CPU/GPU class, workload hash, ceiling, opening time, accepted Leash expiry, stop time and status. But the signed `PlatformQuote` has **no typed Akash owner, deployment sequence, group/order, provider, per-block price, Console account or USDC conversion fields**. Its `hostId` is a Telomere `HostRegistry` entry, not an Akash provider identity. A caller-supplied mapping from the opaque workload hash to those supplier fields would be unsigned and cannot authorize spending. The mounted quote signer and runtime also accept only 120-second CPU/inference tasks, so there is no currently approved path that signs a 3,600-second Akash-specific quote.

The existing contract also settles a run once by `billableSeconds × pricePerSecond` plus optional inference charge and the platform fee, paying the registered Telomere host operator. It has no partial rolling settlement, Akash per-block cost input, Console credit/FX reconciliation or supplier payee. A valid long-duration `PlatformQuote` would therefore still be the wrong financial authority for this product. `SupplierService.activate` must not receive an adapter that infers `approvedRun` from `getRun` alone, and no lease POST should be enabled on that basis.

Before such an adapter is safe, the reviewed supplier contract/quote needs a domain-separated **signed supplier binding** covering the exact Akash account, `dseq/gseq/oseq`, provider, SDL hash, whole-hour runtime, credit account and maximum owner charge. Admission must verify that binding and the owner-funded escrow together at a canonical block, then derive the effective expiry from the minimum of quote runtime, accepted Leash expiry and any owner stop/revocation. Any source of quote data must be persisted and independently matched to the onchain commitment; accepting a JSON object from a caller alongside an otherwise unrelated CPU run is insufficient. Contract-side settlement must enforce exact cumulative supplier costs and refunds independently of the current HostKit meter. Until that versioned authority exists, this module remains read-only accounting and the main controller's `runtime_too_short` blocker remains correct.
