# Python native Vault-income payer

`telomere_sdk.VaultIncomeClient` implements the same exact EIP-3009 payer protocol as the Node client for fixed-price `POST /x402/vault-income`. It sends an external payer's signed authorization to the facilitator. It does not execute a compute task or create an agent service, sign an authorization, hold a signing key, or broadcast an EVM transaction.

The caller must explicitly provide a reviewed **public** profile, a `CryptoVerifier`, an independent reader and a durable journal. The package supplies `RpcVaultIncomeReader` and `FileVaultIncomeJournal`; neither is silently enabled by the client. The profile uses the existing Node field names and contains the exact resource URL, gross amount, native token code/proxy/domain pins, Selection registry/implementation/agent/Vault/treasury pins, facilitator and confirmation policy. It accepts local chain 31337, Base Sepolia 84532 and Base mainnet 8453. Public Base profiles must use Circle native USDC at [the published chain-specific address](https://developers.circle.com/stablecoins/usdc-contract-addresses), a reviewed `circle_proxy` implementation/code pin, a privately reviewed historical `archiveAnchor` (decimal block number and timestamp, canonical block hash), and EIP-3009 version `2`. The EIP-712 name is `USD Coin` on Base mainnet and `USDC` on Base Sepolia; swapping them fails before signing. Former Robinhood `46630`/`4663`, USDG, public facets and other chains fail closed. Local 31337 retains immutable and EIP-1967 fixture support and rejects a public archive anchor.

```python
from telomere_sdk import EthAccountVerifier, FileVaultIncomeJournal, RpcVaultIncomeReader, VaultIncomeClient

reader = RpcVaultIncomeReader(reviewed_rpc_url, profile=reviewed_public_profile)
with FileVaultIncomeJournal(absolute_private_journal_directory) as journal:
    client = VaultIncomeClient(profile=reviewed_public_profile,
                               verifier=EthAccountVerifier(), reader=reader, journal=journal)
    # Choose and retain this ID before requesting the original offer.
    prepared = client.prepare("customer-payment-0001", payer=external_payer_address)
    # The external wallet reviews exactly this typed data and signs explicitly.
    signature = external_wallet.sign_typed_data(prepared["typedData"])
    client.authorize("customer-payment-0001", signature)
    result = client.submit("customer-payment-0001")
    # After an uncertain reply, retry this same ID. After orderly process reopen,
    # construct the same journal/client again and retry the retained original ID.
    result = client.retry("customer-payment-0001")
```

`prepare` durably saves the original plan before returning it. Reusing the operation ID returns a defensive copy of that plan without requesting a replacement challenge. `authorize` verifies the payer's exact EIP-712 signature and commits the original encoded `PAYMENT-SIGNATURE` before returning. `submit` and `retry` send the same resource, POST method, literal `{}` body and original signed header. Amounts are canonical decimal strings of six-decimal token units. Unknown fields, substituted amounts/targets/facilitator/domain/request bindings and signatures fail closed. The normal EOA signature format is canonical 65-byte, low-s, with `v=27/28`.

The first **durably recorded** candidate transaction hash is immutable, including after a reorganization. A candidate is committed before requesting independent evidence. Storage failures cannot return success. HTTP 200 or a facilitator receipt never establishes settlement by itself. `check` returns `planned`, `authorized`, `submitted`, `pending`, `settled` or `reverted`. Every terminal return rechecks independent evidence; prior success is durably changed to pending before that request, so lost RPC evidence, confirmation depth or canonical history cannot return cached financial success.

A submitted, unresolved authorization blocks new first submissions and authorizations for that payer. The exact submitted retry remains available, even when one reorganization orphaned several earlier payments. A reverted outer transaction leaves the bearer authorization valid: another payment stays blocked until a fresh independent confirmed block reaches its expiry and another inspection still proves canonical revert plus unused authorization/ref markers. Expiry does not resolve a missing candidate or an authorization consumed under another transaction hash.

## Caller journal contract

`exclusive(scope, callback)` synchronously serializes every client instance sharing that scope. The callback receives `load()` and `save(state)`. `load()` returns the original complete JSON state or `None`; `save()` atomically commits and durably flushes the complete supplied state **before returning**, including when the surrounding callback later raises. It must not roll back writes on callback errors. Return independent objects rather than aliases. One process owns the journal; shared storage requires appropriate cross-process exclusion and a safe owner-recovery policy.

The signed authorization is a bearer payment instruction. Protect live storage, backups and exports with private ownership/ACLs and appropriate encryption; do not log headers, raw plans or journal state. The client rejects concurrent calls per instance, duplicate operation/challenge/nonce identities, corrupted signatures and changed profile bindings. Storage is bounded to 128 retained attempts and 1 MiB. There is no automatic pruning; retain unresolved attempts and their original evidence.

`FileVaultIncomeJournal` owns one absolute local directory and one reviewed profile. With `create=True` (the default) it creates only a missing leaf directory; parents must already exist. New POSIX directories/files use exact owner-only `0700`/`0600`. Windows creates protected ACLs for the current user, SYSTEM and Administrators. Existing ownership/permissions are checked and never repaired. Null/overbroad ACLs, hardlinks, symlinks, reparse points and unsafe ancestors fail closed. POSIX uses an anchored directory descriptor and `O_NOFOLLOW`; Windows holds ancestor directory handles denying rename/delete while the journal is open. Reads compare named/opened identities and metadata, remain size bounded, and reject corrupt JSON before executing a callback.

Each save writes an exclusive random private temporary file, flushes its complete contents, atomically replaces `state.json` in the same directory and flushes the directory on POSIX. Windows uses write-through file creation and `MoveFileExW(REPLACE_EXISTING|WRITE_THROUGH)`. A later callback exception cannot roll back a committed save. Failed writes/replacements leave the previous state; failure after replacement preserves the committed state for reconciliation. Escaped/cross-thread transactions, nested ownership resets, inherited fork owners and changed directory/lock identity are rejected.

The persistent `.owner.json` lock is created exclusively and retained for the open object's lifetime. Use the context manager or `close()` for orderly reopen. **A crash intentionally leaves the lock.** After independently establishing that the previous process has stopped and cannot resume writes, an operator may explicitly recover that private directory by removing the abandoned owner lock while preserving `state.json`. The adapter never steals a lock, treats a PID alone as sufficient proof or silently replaces an existing owner's file. Shared/network filesystems are unsupported; local atomic-replacement and durable-flush semantics are prerequisites. Files contain bearer authorizations under private permissions, without application-level encryption. Tests establish failure/reopen behavior, not power-loss survival or a filesystem-independent crash guarantee.

## Independent reader boundary

`RpcVaultIncomeReader` uses a separate reviewed HTTPS RPC, or literal loopback HTTP for local chain 31337. It has an explicit read-only method allowlist, no wallet/account key and no broadcast path. The optional pinned Ethereum dependency set supplies keccak, EIP-712 verification, RLP and transaction-signature recovery; no new dependency is added. `reader.profile` is a defensive copy and is checked against the client profile on every evidence request. `check()` first requires the public Base RPC to serve the privately pinned canonical anchor at least six hours behind the current head, including exact native USDC proxy code, Circle implementation slot/code, direct metadata, domain and six decimals at the old block. It then verifies the same asset pins at confirmed and current blocks, plus registry/Vault implementation/clone/constructor/agent bindings. The EIP-1967/facet checks remain available only for local fixtures. It also derives the canonical Selection agent ID from chain, registry, immutable identity registry and returned identity ID. The archive probe proves that specific old state is available now, not future retention. `inspect(transaction_hash=..., payment=...)` independently verifies:

- Original signed raw EIP-155 legacy, EIP-2930 or EIP-1559 transaction bytes, their hash and recovered facilitator, exact chain/Vault/zero native value and complete calldata including the original payer authorization. Other envelope types fail closed. Only an explicit numeric JSON-RPC `-32601` for the raw method permits reconstructing the complete signed type-2 envelope; remote error messages never select that fallback. Missing/surplus/changed signed fields, noncanonical quantities, zero/high-s signatures and changed access lists cannot establish settlement.
- Current and receipt-block deployment/code/domain pins and canonical receipt block with sufficient confirmation depth, freshly rechecked at each terminal return.
- Original token authorization and native Vault reference consumption, exact original-payer Income/Subsidy events and per-transaction token transfer conservation. The payer in the authorization remains the income source, rather than the facilitator.
- Rounded-up 1% fee for actual Income, zero fee for Subsidy, exact gross/net/ref/payer binding. A canonical reverted result also proves unused original markers. Expired authorizations and later freeze/Death do not erase valid historical receipts.

Owner, the target agent wallet, controller, treasury, registry and registered wallets/Vaults in the same family remain Subsidy. The concrete reader recomputes that predicate at the exact classification log: it starts with canonical parent-block registry mappings and replays only canonical ordered `Birth` additions before the classification's global `logIndex`. The reviewed contract assigns owner, wallet, family and these mappings only at `_birth`, so immutable born-agent fields can be checked at the receipt block. Later registrations in that block cannot relabel an earlier payment. Nonzero mappings returning an unknown or incorrectly derived agent tuple fail closed. This proof requires parent-block registry code/state and a complete bounded query of at most 1,024 Birth logs; payment in the registry's initial deployment block fails closed. The actual same-block payment-before-family-registration test preserves the original Income classification and rounded fee.

Every contract state read uses EIP-1898 `{blockHash,requireCanonical:true}`. Terminal results recheck both deployment and receipt canonicality/confirmation depth. A missing candidate with consumed original markers requires reconciliation, rather than becoming an expired or refunded payment. Base USDC rechecks the Circle implementation slot, pinned code and domain at the original receipt block and current head, requires the pinned parent-block implementation, and rejects `Upgraded(address)` logs from the proxy in the receipt block. Local EIP-1967/facet fixtures additionally check pinned parent-block authorization routes and reject ordinary `FacetUpdate`/`Upgraded` events in the receipt block. This does not replace execution tracing against a malicious implementation that silently rewrites proxy storage. The RPC remains the trusted source of canonical chain data; this is not a light client or receipt-trie proof.

The client also checks strict evidence fields, deterministic Solidity ABI/keccak reference, exact candidate/payer/gross and fee arithmetic. A custom reader remains the caller's trusted evidence boundary and must meet the same full contract; consistency checks alone cannot establish that an injected reader performed those checks. Target RPC compatibility, historical block-hash retention, deployed Base contracts and funded public acceptance still require their separate release checks. The original `TelomereClient.receipt()` evidence flags keep their existing pilot scope; the new reader applies only to native Vault-income intake.

## Public transport

`VaultIncomePublicHttp` uses a fixed public origin/path and sends no cookies, session authorization or wallet keys. It follows no redirects and reads no proxy settings. HTTPS is required except literal `127.0.0.1`/`[::1]` HTTP on chain 31337. It caps JSON at 16 KiB, headers at 40 fields/8 KiB, payment headers at 8 KiB and the complete request at at most ten seconds. Duplicate JSON keys, invalid UTF-8, BOM/NUL/surrogates, duplicate critical headers, contradictory framing and malformed canonical base64 fail closed. Socket shutdown interrupts trickling headers/body. A single guarded daemon worker bounds caller latency even if system DNS or connect stalls; the transport stays busy until that worker exits, preventing accumulation or a late payment POST after the original deadline. Custom transports become the caller's trusted network boundary and must retain these properties.

RPC has its own ten-second retained deadline, 32 KiB request bound and 256 KiB response bound, with the same header/strict JSON/redirect/credential protections and no retries. Several bounded RPC calls are required for one proof; the per-request deadline is not a single ten-second bound for the complete proof or caller journal I/O.
