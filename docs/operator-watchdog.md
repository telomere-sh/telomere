# Read-only operator watchdog

Current network target: Base 8453 / Base Sepolia 84532 with native USDC. Dated acceptance and linked JSON evidence retain their original network/source scope; see [migration record](base-usdc-migration-2026-10-14.md).

The existing `operator:status` command checks the configured chain, escrow and token identities, signer nonce and gas, controller readiness, PostgreSQL finance journal and NEAR readiness. This watchdog runs that diagnostic repeatedly and turns its public snapshot into stable alert codes. It does not submit transactions, cancel runs, touch provider accounts or change controller state.

Before running it, provision a directory owned by the operator with mode `0700` on Linux, outside Git and the backup output. Pass a state file **inside that existing directory**. The watchdog refuses symlinked directory ancestors, symlinked state files, public POSIX parent/state permissions, corrupt state and a crash-held lock. A lock left after a crash must be inspected by an operator before removal. The state contains only codes, severity, timestamps and occurrence counts. It contains no RPC URL, token, private key, run ID or provider response.

Run the TypeScript source with `npm run operator:watchdog --` or the compiled script with Node. Example, using **reviewed public deployment pins** and a private profile path:

```sh
npm run operator:watchdog -- \
  --env-file=/opt/telomere/profile.env \
  --state-file=/var/lib/telomere/watchdog/state.json \
  --expected-mode=testnet \
  --expected-chain-id=<reviewed-chain-id> \
  --expected-escrow=<reviewed-escrow-address> \
  --expected-token=<reviewed-token-address> \
  --expected-signer=<reviewed-public-signer-address>
```

All expected values are required. Compare them with the reviewed deployment record, not values copied from the running profile. `--expected-escrow` and `--expected-signer` pin the original pilot escrow and signer observed by `operator:status`; the paid platform has a separate escrow and signer. The watchdog does not accept paid-journal pins or run the manual paid signer audit. `--api-url` overrides the controller origin; `--interval-ms` accepts 30,000–300,000 milliseconds (default 60,000). `--once` performs one check and exits nonzero for a warning or critical state, making it suitable for a local service manager check. In continuous mode each cycle writes one compact JSON line with health, active codes and raised/resolved transitions. It never directly notifies an external recipient. Configure the service manager or log collector to page the operator on critical codes and to detect a stopped watchdog process.

Each child invocation is the repository's fixed `operator-status` script without a shell. Its stdout is capped at 256 KiB, its run time at 60 seconds and its stderr is discarded rather than buffered or logged. A nonzero exit remains a critical code even if the JSON otherwise parses. Failed, malformed, stale or incomplete diagnostics fail closed and retain previously observed specific faults until a fresh complete snapshot confirms their resolution. Critical states include mismatched reviewed pins, chain/signer/token checks, unavailable controller or worker, missing controller DB lock, unresolved finance journal, reconciliation and pending receipts. An aged queued job, a `running`/`near_dispatching`/`settling` job with no update for 15 minutes, low operator gas and pending signer transactions are warnings. The 120-second queue, 15-minute active-job and 0.001-ETH gas thresholds are local defaults, not economic release policy.

The same read-only PostgreSQL snapshot also checks paid `platform_runs`, even if the platform route is currently disabled. Unknown paid statuses and any `reconciliation` row are critical. Queued work older than two minutes, a `running` row with no update for 15 minutes, and `receipt_pending`/`settling` work whose original quote is over two hours old raise warnings. A final Vault row without a recorded sync also warns once its original quote is over two hours old. Queued and financial ages use the original creation time because retries update `updatedAt` and must not hide a stuck payment. The watchdog publishes only counts, timestamps and stable alert codes; no owner, run ID or private finance row enters its durable state.

On older staging deployments without a `platform_runs` table, the diagnostic reports `platform.status=not_installed` and continues monitoring legacy finance. If the profile configures a paid platform but the table is missing, the diagnostic fails closed. When the table exists, the watchdog inspects it even when the paid route is later disabled, so persisted work remains visible.

When two-S3 large-Cyst replication is configured, `operator:status` independently rereads the pinned private destination file and the immutable local topology marker. It then sends a signed **GET only** to each destination's existing canary, verifying exact bytes and metadata, and reads the controller's `/api/config` flags for `largeCystsReplicated` and `largeCystsWritable`. `storage.status=ready` requires the same bound topology, two readable canaries and a running controller that reports this replication mode as writable. The watchdog raises `large_cyst_unobserved` if the pin, topology or controller response cannot be trusted; `large_cyst_destination_unavailable` if a checked canary is inaccessible or invalid; and `large_cyst_read_only` if the running controller entered read-only mode after a startup destination failure. These are critical alerts. The snapshot exposes only ordinal destination states and fixed reason codes, never endpoints, buckets, credentials or object contents. A profile without the two-S3 configuration reports `storage.status=not_configured` and performs no storage probe, preserving older local-only staging.

The canary GET proves current read access and integrity of one immutable object. It cannot prove that conditional PUT remains available after startup, audit every checkpoint part, or establish that the two providers are independently operated. The public controller flags prove the replication mode and read-only state, but do not expose its exact private destination identity; deploy the operator profile and controller from the same reviewed configuration. A controller that booted read-only stays read-only until restarted after recovery; the diagnostic keeps that state visible even when both canaries later read successfully. Provider write failures after a healthy boot must also be handled by the write path and incident response. The storage check takes no writer lock, changes no objects and does not repair data.

The status source reflects the pilot controller's diagnostic fields and PostgreSQL summaries. `prepared` paid quotes remain visible as a count and oldest timestamp, but do not alarm on age: unused quotes persist indefinitely, while an EOA might have opened a run onchain before losing the admission HTTP response. The separate read-only `operator:platform-prepared` command compares each bounded prepared quote with pinned historical chain state. Run `operator:platform-journal` separately in a reviewed quiescent release window to audit signed paid transactions and canonical receipts. Its full historical scan is not safe as a minute-by-minute pager: normal in-flight transactions can appear as missing receipts or nonce changes, and its 4,096-row cap needs an archival plan. Continuous paid signer journal coverage remains an open launch task. The watchdog does not monitor GPU Cells or supplier accounts. It does not establish uptime, recovery runbooks, funded Base acceptance or independent security review. Those checks remain release gates. The focused offline tests cover real snapshot shape, pin drift, paid and legacy finance alerts, crash/restart deduplication, resolution, corrupt private state, secret-safe output, child process bounds and the two-S3 read-only probe. An earlier pinned, isolated Linux staging run verified `ok` → pin mismatch → `ok` alert transitions without changing the five live services; see `operator-watchdog-linux-validation.json`. That run predates the two-S3 signal.

The private demo VPS now runs the pinned `infra/telomere-staging-watchdog.service` under systemd. Its first restart exposed a timer that ignored `SIGTERM`; the corrected source aborts the diagnostic child and timer without recording a false alert. The exact corrected archive built on that host, passed 18/18 Linux watchdog tests, and the installed source files matched the archive. The service then restarted cleanly, with `ok` health, persistent sequence and all five existing services active; see `staging-watchdog-deployment-validation.json`. This is **private local-chain staging** with no paid platform route or independent S3 configuration. It writes to journald but has no external pager/log collector; those and a paid Base deployment remain acceptance gates.
