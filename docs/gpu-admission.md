# GPU admission slice (M4)

The backend now has a separate GPU admission boundary in `src/gpu`. It is not mounted in the current CPU HostKit runtime or the financial scheduler, so this work **does not** make GPU jobs available to users. It adds the fail-closed checks that a GPU runtime must satisfy before M4 can be connected.

`GpuAdmissionController.prepare(uuid, runId)` takes an atomic `O_EXCL` claim for the GPU UUID in an operator-owned state directory. It queries `nvidia-smi` without a shell under a shared five-second inventory deadline and a 16 KiB output cap. The query checks driver major, total/free framebuffer memory, current/default power ceilings, exclusive-process compute mode, MIG disabled or unsupported, and active compute processes. Hex letters in GPU UUIDs are canonicalized before duplicate and active-process checks, so a differently cased process UUID cannot make the same device appear idle. An absent, malformed, unsupported, duplicated or busy device fails admission. The claim survives a process crash, requiring explicit operator reconciliation rather than silent reuse.

The controller then sends fresh 256-bit nonce and seed challenges to a `GpuProbeDriver` bound to the exact run ID, GPU UUID, approved image digest, and either gVisor with nvproxy or Kata GPU isolation. The class probe must fall inside the configured GEMM and memory-bandwidth band. The memory probe must report a full write/readback of the configured VRAM amount with integrity success. Both reject throttling, stale/replayed/challenge-mismatched reports and incomplete cleanup. The GPU is re-inventoried after both probes, including a second power and occupancy check. Unknown probe cleanup quarantines the claim on disk.

The returned `GpuPreparedRun` retains that claim. `warmCheck(runStartedAtMs, workloadCellHandle)` requires another challenge bound to the same run ID inside that run's Cell during its first 20 seconds; launching a second tenant for the warm probe would violate the isolation policy. The admission `GpuProbeDriver` handles only disposable class and memory probes; the warm kernel runs through the workload Cell handle. `billableReady` remains false until it passes, and becomes false again after confirmed cleanup/release. The HostKit adapter also excludes the full first 20 seconds from user billing, even if the warm kernel finishes earlier. A failed warm kernel keeps the durable GPU claim for operator review. Releasing a successful run's claim requires independently confirmed exact Cell cleanup.

The configured class bands are operator-reviewed policy values, not numbers inferred from a self-reported device label. The probe report hash is an audit correlation value, **not proof of execution or a signature**. A software host can lie about its own hardware. The adapter deliberately has no default implementation: a production `GpuProbeDriver` must launch a reviewed fixed-seed CUDA image through a real isolated GPU cell, bind the physical UUID, perform the kernels and memory readback, and prove container cleanup. Passing a remote JSON object to this interface would be a trust-boundary violation. The file claim coordinates Telomere processes on one machine; NVIDIA exclusive-process mode restricts contexts, but neither mechanism attests an adversarial host or proves device assignment across a remote provider.

Before GPU launch, implement and independently exercise that CUDA driver on the actual Linux host, verify nvproxy or Kata passthrough isolation, connect the adapter to HostKit admission/metering and financial settlement, test one tenant per physical GPU during simultaneous requests and restarts, publish class bands from measured hardware, run admission/daily/random memory probes, and record real throttled and misreported-VRAM failures. The current Windows tests use simulated `nvidia-smi` output through real child processes and deterministic fake probe drivers; they do not constitute hardware, CUDA, nvproxy, or Kata acceptance.

NVIDIA's [nvidia-smi manual](https://docs.nvidia.com/deploy/nvidia-smi/index.html) documents UUID-stable addressing, compute modes, selective read-only queries and power limit reporting. Run `npx vitest run tests/gpu-admission.test.ts` and `npm run typecheck` for this module.
