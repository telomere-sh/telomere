# Optional Base spend-permission CPU funding

This is a separate deployment profile for an EOA owner's bounded CPU reservations. A separately approved smart funding account supplies USDC through the SpendPermissionManager. The original EOA remains the quote payer, Leash owner and refund beneficiary. The funding account's approval explicitly authorizes that destination; no relationship between the two accounts is inferred.

The new `PlatformSpendPermissionEscrowV1` uses the `TelomerePlatformEscrow` EIP-712 domain version **3** and distinct reviewed escrow bytecode pins. Optional `pins.spendPermissionProfile` contains `kind: "base_spend_permission_v1"`, `managerAddress` and `managerCodeHash`. It cannot be combined with economics-v2 domain 2. Existing v1/v2 contracts, domains, quotes and persisted inputs retain their original meaning. Public Base profiles require the canonical Manager address and independently reviewed runtime code hash. Local Anvil uses explicit local fixture pins.

## Owner approval and exact opening

The funding account approves an official Manager permission with `spender` equal to the new escrow and `token` equal to its immutable USDC. Its exact `extraData` binds the funding account, chain, escrow, EOA refund beneficiary, original Leash identifier and a hash of the original agent, hourly/daily caps, scope roots, class mask, sealed-only flag and expiry. Changing those Leash terms invalidates this approval. The owner reviews the permission's allowance, recurring period, start and end; the backend never approves it or receives a smart-account signing key.

An ordinary EOA quote may include `funding: { kind: "base_spend_permission_v1", permission }`. The controller independently reads one canonical confirmed Manager/account snapshot, checks approval, exact signed type, remaining period allowance, token balance and the bound Leash. This is a planning observation, not a balance credit or a fund reservation. The ordinary escrow balance API continues to report only actual escrow funds.

The checked SDK returns an exact unsigned `openRunFromSpendPermission` transaction and explicit `fundingReview`: funding account, EOA refund beneficiary, conservative reservation ceiling, permission hash and Manager address. The external EOA/agent wallet submits it. The escrow pulls the complete conservative ceiling once through the pinned Manager, then applies the same signed quote, host, Leash and reservation rules atomically. If admission fails, the Manager's allowance consumption and token movement revert with it. The funding account is not reported as Selection income; this path funds an EOA reservation.

The controller admits only the original canonical transaction and expected funding method. A funded preparation cannot be silently replaced with an ordinary balance opening, and an ordinary preparation cannot be relabeled after a permission-funded opening. The independent funding reader verifies exact calldata, the original permission, `RunOpened`, historical run fields, the Manager's usage event and exact USDC conservation. Historical verification does not require an expired permission to become valid again.

Settlement uses the existing signed meter/receipt path. Unused reservation returns to the explicitly approved EOA's escrow balance, where that owner can withdraw it. It does not automatically return to the separate funding account and does not replenish its consumed Manager allowance. Owner/agent authentication retains the existing EOA scope.

## Supported boundary

This first profile supports ordinary CPU receipt-v1 tasks and sessions. Vault runtime, CPU receipt-v2 issuance, economics-v2, inference-only tasks and CPU-plus-inference combinations are rejected early. A Vault funding shortcut would bypass its existing `payRun`/Selection exposure accounting, so it is deliberately unavailable. Python clients retain their old strict profile handling and reject this new unsupported profile rather than guessing its domain or calldata. Smart-account authentication, passkeys, ERC-6492 and automatic Manager approval are outside this profile.

The [reference Manager fixture](../tests/fixtures/spend-permissions/README.md) retains actual compiled upstream code and its complete reproducible source input. Local fixture acceptance is separate from public Base funded acceptance and from a verified public Manager deployment. Do not advertise this profile as complete Base Account integration or public launch readiness solely from Anvil tests.

A subsequent [public provenance check](base-spend-permission-public-provenance-2026-10-15.md) authenticates the original metadata and sources and exactly reproduces the full deployed Manager runtime on Base and Base Sepolia. That read-only evidence does not enable a public profile or replace actual account approval and funded compute acceptance.

The [15 October focused acceptance](base-spend-permission-validation-2026-10-15.json) passed both final actual Anvil cases, including HTTP CPU execution, positive settlement, exact refund destination and bidirectional funding-method rejection. Both standalone readers also rejected a wrong USDC code pin against the actual valid funded opening. The 16 captured core/test/reference files were identical before and after that run and still matched when the result was recorded. The preceding pass and earlier failed fixture attempt are retained. A separate preceding legacy client/runtime regression passed 72 cases. These are focused results; they do not establish a frozen whole-backend release or public Base acceptance.
