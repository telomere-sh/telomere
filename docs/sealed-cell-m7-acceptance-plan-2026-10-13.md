# M7 sealed CPU Cell: integration and acceptance gate

**Status, 13 October 2026:** M7 remains required after arbitrary GPU Cells became optional. The current key-release module is a local, default-unmounted cryptographic boundary. It does not attest a Telomere Cell, deploy a confidential CPU runner, or restore a checkpoint inside one. Its unit tests use a verdict fixture and cannot authorize production release. The managed NEAR model-inference attestation covers NEAR's serving workload and TLS signer, not a Telomere-controlled recipient key or CPU Cell. Do not wire a NEAR inference verdict or Enclave's software `DevCvm` descriptor into `SealedCellHardwareVerifier`.

The release API now creates a random owner challenge and a deterministic 64-byte expected TD `report_data` **before** invoking `SealedCellEvidenceCollector`; it calls the collector and verifier once, rejects missing/oversized evidence and cancellation before vault access, and never retries an uncertain verification. The first 32 `report_data` bytes commit to every request selector and the challenge, and the final 32 bytes are the raw challenge. A local fixed vector and selector-mutation tests lock the encoding. This removes the earlier API ordering flaw and gives the guest and verifier an exact byte contract. Neither ordering nor expected-byte comparison proves freshness by itself: an independent verifier must authenticate a real quote and extract its actual `report_data`. A callback that returns cached bytes, or a fixture that echoes the expected verdict, must remain a rejection in production. The optional [signed appraiser transport](signed-cell-appraiser-transport.md) now authenticates a separately operated verifier's response against an operator-pinned Ed25519 key and checks exact quote/challenge/profile bindings, but no independent Cell appraiser service or hardware acceptance is present.

## Missing resources and code

1. **An actual CPU TDX Cell:** obtain an owner-approved Intel TDX host or a NEAR-managed custom CPU CVM entitlement that permits the exact Telomere runner image, a guest quote API, start/stop/fencing, and an authenticated transport to the owner. The inspected VPS has no `/dev/tdx*` or `/dev/kvm`; its NEAR key grants model inference only. The pending NEAR dedicated-deployment request has not allocated a CVM. GPU hardware is unnecessary for this M7 CPU path.
2. **Reviewed guest and quote policy:** pin the measured runner/image digest, full Intel TDX measurement vector, allowed TCB/advisories, debug-disabled status, Intel DCAP trust roots/collateral, key-generation code, quote API and policy validity window. `teeMeasurement` in the current TypeScript request is a 32-byte identifier; it cannot stand in for all raw TDX measurements. Define it as the digest of the independently reviewed measurement profile, then compare every actual quote field to that profile. Pin the exact policy bytes under `policySha256`; never accept caller-provided policy or an auto-renewed measurement.
3. **Hardware verifier implementation:** add a dedicated, operator-owned `SealedCellHardwareVerifier` adapter that parses raw Cell quote/evidence and verifies its signature, collateral freshness/revocation, platform/QE TCB, debug flag, full measurements and event log. Implement the now-frozen `sealedCellReportData` encoding in the guest and independent verifier, validate its fixed vector across languages, and compare the authenticated quote's 64-byte report-data field byte-for-byte to the expected value. Derive the verdict from verified quote plus reviewed local policy and canonical run/checkpoint state; never copy a verdict from HTTP JSON or a caller-selected adapter. The existing `infra/near/verifier.py` contains DCAP checks for NEAR model/Gateway reports, but its report-data layout binds NEAR signers/SPKI and is not this Cell protocol.
4. **Authenticated guest key and packet delivery:** generate the non-exportable X25519 private key inside the measured Cell and keep it there. Authenticate the quote/key correspondence and current Cell instance to the owner. Deliver the encrypted packet over a channel bound to that instance. The guest must also authenticate the owner/packet origin, or independently authenticate the canonical checkpoint manifest and ciphertext before using the recovery key. X25519 encryption alone does not authenticate who sent a packet. The present `openSealedCystKey` helper checks context and freshness but does not implement that sender authentication or lifecycle fencing.
5. **Production wiring:** mount the collector/verifier only from reviewed operator configuration, not from a user request. Connect release to a current canonical paid run, HostRegistry identity, active fenced Cell lease and latest completed Cyst checkpoint. The existing `releaseCystKeyToSealedCell` and `openSealedCystKey` have no production call sites. Do not expose an endpoint that permits a caller to inject a verifier function. Persist secret-free release/denial audit records and disable the route if collateral, policy, lease, host or deployment pins become unavailable.

## Acceptance on the exact deployment

- On actual TDX hardware, capture a fresh quote only after receiving the owner challenge. Independently appraise authentic quote signatures and current collateral; reject `OutOfDate`, revoked or advisory-disallowed TCB, debug mode, changed runner image, event log and any wrong policy field. Preserve the raw evidence privately and record only bounded hashes/status in routine logs.
- Prove that a quote for a previous challenge, another recipient key, another run/host/checkpoint, a copied NEAR model quote or an unapproved Cell measurement yields **no vault read and no key packet**. Repeat under restart and cancelled/expired verification; no automatic retry may release to an uncertain instance.
- In the measured guest, authenticate the packet source, open the key, decrypt the exact canonical checkpoint and resume an application-state workload. Show that the key never appears in the owner-to-guest transport as plaintext and cannot be used by a second Cell. Reject a forged packet, changed registry revision or stale lease before publishing restored state.
- Kill/restart the Cell and owner process at each handoff boundary, including after quote collection and after packet transmission. Reconcile unknown delivery without weakening the challenge or double-starting a billable run. Verify host-loss recovery on a distinct physical host if that capability is claimed.
- Run the current and adversarial checks against the pinned production image, verifier binary, exact policy bytes and current hardware collateral. Obtain independent security review before enabling public sealed-key delivery. Unit verdict fixtures and the existing NEAR inference proof remain engineering tests only.

No additional M7 completion percentage is assigned for the challenge-order fix or this plan. Operational M7 acceptance remains blocked until the Cell hardware, authenticated verifier, production wiring and end-to-end restore above exist.
