# Signed type-2 transaction RPC fallback

Current network target: Base 8453 / Base Sepolia 84532 with native USDC. Dated acceptance and linked JSON evidence retain their original network/source scope; see [migration record](base-usdc-migration-2026-10-14.md).

This addendum supersedes the raw-RPC-only requirement in the original checked Vault income client guide. `RpcVaultIncomeReader` first requests `eth_getRawTransactionByHash`. Only an actual JSON-RPC `-32601` response enables a second request to `eth_getTransactionByHash`. A missing raw transaction, timeout, malformed response, authorization failure, or another RPC error does not enable reconstruction.

The fallback accepts complete signed EIP-1559/type-2 fields: chain ID, nonce, gas, recipient, value, input, access list, both fee caps, parity, and both signature scalars. It serializes those fields with viem, checks that the signed envelope hashes to the already retained candidate hash, recovers the pinned facilitator, and verifies the exact native Vault calldata. Signature scalars may be canonical uint256 quantities or 32-byte data; they are normalized without changing their numeric values. Missing fields, unsupported transaction types, overflows, inconsistent parity, invalid scalars, changed signed fields, or an altered hash fail closed. Reconstructed envelopes retain the existing 8 KiB byte limit and bounded RPC transport.

Successful reconstruction alone does not prove payment. The reader still independently checks the current and historical token, Selection, implementation and Vault pins; original payer signature and request binding; canonical receipt and confirmation depth; consumed authorization/reference; exact classification events and fee conservation. Public Base USDC implementation pointer and bytecode are checked using the Circle slot; receipt blocks with upgrades are refused. Old USDG authorization-facet pins are not accepted for Base. The caller's durable candidate and exact authorization remain immutable, including after ambiguous HTTP responses and reorgs.

This change does not enable a public asset profile or deploy anything. A provider must also retain canonical hash-addressed historical state for the receipt block. If those state reads expire or become unavailable, inspection fails closed; it never substitutes latest state. Archival retention is a separate release requirement for delayed verification. Legacy and other typed transactions still require the original raw signed RPC path.

Local acceptance uses real Anvil transactions and actual HTTP JSON-RPC responses, including income/subsidy, a nonempty access list, minimal-length signature quantities, omitted signed fields, tampered fields, overflows, and non-`-32601` failures. No public transaction or payment is used by these tests.
