# M7 signed Cell appraiser transport

`src/sealed-keys/signed-appraiser.ts` is a **default-unmounted owner-side transport adapter** for a separately operated Intel TDX quote appraiser. It does not verify a quote signature itself. It must only be configured by an operator, with the appraiser's reviewed Ed25519 public key, validity window, fixed HTTPS endpoint, current policy SHA-256, and the complete reviewed TDX measurement vector. There is no user-controlled verifier selector or secret key in this module.

The owner sends raw bounded quote bytes plus its one-shot challenge, exact 64-byte expected `report_data`, run ID, recipient X25519 public key, measurement-profile digest and policy digest to the fixed appraiser. The appraiser must independently verify the **raw** quote signature, Intel root and current collateral, QE and platform TCB, debug-disabled attributes, all TDX measurements and the workload event log before it signs a result. Intel's [TDX runtime guide](https://cc-enabling.trustedservices.intel.com/intel-tdx-enabling-guide/07/trust_domain_at_runtime/) documents the 64-byte REPORTDATA quote input. The [dcap-qvl verifier documentation](https://github.com/Phala-Network/dcap-qvl/blob/master/README.md) describes quote, collateral and current-time checks, and [Intel's TCB guidance](https://www.intel.com/content/www/us/en/developer/articles/technical/software-security-guidance/best-practices/trusted-computing-base-recovery.html) explains why `OutOfDate` is not an acceptable `UpToDate` result here. The existing NEAR inference verifier uses a different report-data protocol and cannot act as this appraiser.

The accepted response is exact canonical JSON containing `payloadB64` and `signatureB64`. The Ed25519 signature covers UTF-8 bytes `telomere.sealed-cell.signed-appraisal.v1\0` followed by the decoded canonical JSON payload. The signed payload fields, in order, are `version`, `verification`, `evidenceSha256`, `challenge`, `reportData`, `runId`, `recipientPublicKey`, `teeMeasurement`, `policySha256`, `verifiedAtMs`, `expiresAtMs`, `collateralExpiresAtMs`, `quoteStatus`, `qeStatus`, `platformStatus`, `advisories`, `measurements`. The full TDX measurement vector uses the fixed field order in the source; `teeMeasurement` is SHA-256 of the canonical array prefixed with `telomere.sealed-cell.tdx-measurements.v1`. JSON with duplicate fields, unknown fields, altered order, whitespace changes, malformed base64 or a different signing key is rejected. This exact-byte contract needs an independently implemented appraiser before live deployment.

The adapter checks the signature **before** interpreting the payload, then compares the signed quote SHA-256, challenge, authenticated `report_data`, run/key/policy selectors, all 14 pinned TDX fields and debug bit. It accepts only `UpToDate` quote, QE and platform statuses, no advisories, current collateral, a non-expired signer pin, and a result issued during the current one-shot verification window. It limits raw quote and reply size, uses HTTPS with redirects refused, and applies an abortable 45-second maximum. Any mismatch throws before `releaseCystKeyToSealedCell` can read the checkpoint vault. The returned `hardware_verified` verdict means the **pinned external appraiser** asserted and signed that result; signature verification alone cannot establish hardware authenticity.

The 16 transport tests generate an ephemeral Ed25519 fixture key and sign simulated appraisals. They cover quote-hash, nonce, report-data, run, recipient, profile, policy, TCB, collateral, signer and JSON malleability failures, including a no-vault-read release attempt. The quote fixture is synthetic bytes, **not** a captured TDX quote. No real appraiser endpoint, Cell guest, signed live hardware evidence, current collateral, measured key-generation path, guest packet-source authentication or restored workload has been accepted. The M7 hardware and end-to-end gate in [the acceptance plan](sealed-cell-m7-acceptance-plan-2026-10-13.md) stays open.
