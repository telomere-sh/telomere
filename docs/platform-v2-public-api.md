# Platform v2 verification and evidence retrieval API

Current network target: Base 8453 / Base Sepolia 84532 with native USDC. Dated acceptance and linked JSON evidence retain their original network/source scope; see [migration record](base-usdc-migration-2026-10-14.md).

When the reviewed Platform runtime is configured, the main server mounts `POST /api/platform/public/v2/verify` without a wallet session. The request is a strict JSON object with `openTransactionHash`, `settlementTransactionHash`, and the redacted v2 `core`. The caller cannot choose the RPC URL, deployment pins, or confirmation depth; the route receives the configured read-only Platform bridge with twelve confirmations by default, or the opt-in issuer's reviewed depth. Public issuer configuration requires at least twelve. Query parameters and extra body fields are rejected. The main server's existing POST policy requires its exact configured `Origin` and JSON media type, and its public-financial rate bucket permits six requests per minute per socket IP, shared with the other public financial routes. `createPlatformV2Routes` also remains available for embedding with an explicitly reviewed server-side depth.

The route calls `verifyPlatformV2CombinedEvidence`. A successful response means that this **caller-presented** core matches a canonical confirmed settlement and financial root, the original canonical opening authority, and the signed ordered tick/ACK sequence contained in the committed core. The archive opening's `blockNumber` and `confirmations` are returned as decimal strings; financial amounts and its confirmation count already use decimal strings. The verdict retains `independentlyPublished: false`, `historicalDelegationIssuanceTimeProven: false`, `physicalTickStreamCompletenessProven: false`, `executionStatusProven: false`, and `outputVerified: false`.

The verifier does not issue or upgrade receipts. [Explicitly enabled CPU v2 issuance](platform-v2-issuance.md) now commits the actual host-signed admission receipt and the signed paired meter history; the default runtime and existing financial rows remain v1. A core without the optional admission preserves its original digest and returns `hostAdmissionVerified: false`. For an admitted core, the archive reader also checks its opening transaction and block against canonical chain history. Supplying an ordinary v1 settled run fails verification.

When the reviewed v2 publisher is configured, `GET /api/platform/public/v2/runs/<runId>?settlementTransactionHash=<hash>` retrieves both configured evidence copies, verifies their manifest and core, then verifies the canonical opening and settlement/root and rechecks both copies. It returns `{ verification, core, publication }`; opening bigint values inside `verification` are decimal strings. No wallet session is needed. The sole query field is `settlementTransactionHash`; caller-selected endpoints, pins and RPC are rejected. An unavailable publisher or missing/divergent evidence returns a sanitized 503. GET never writes or repairs evidence. Both GET and POST share the four-request concurrency bound and the main server's public-financial rate bucket. GET reports `configuredCopiesVerified: true` on success while retaining `independentlyPublished: false`, since physical and administrative storage independence requires separate acceptance.

The [independent receipt CLI](platform-v2-cli.md) performs the same checks directly against separately supplied deployment pins and RPC, without an API session, database, wallet, or operator key.

The request body is limited to 300 KiB of actual bytes, and the core retains its 256 KiB verifier bound. Body receipt has a five-second deadline. At most four requests can read or verify concurrently. A response timeout is 30 seconds; its slot remains occupied until the underlying RPC verification settles. Slow request bodies retain their slot until cancellation cleanup completes. Responses disable caching. Invalid JSON returns 400, a slow body 408, an oversized body 413, wrong media type 415, schema violations 422, and exhausted capacity 429. A cryptographic rejection or RPC uncertainty returns the same sanitized 503 response because the combined verifier does not expose a reliable typed distinction at this HTTP boundary; internal verifier messages are never returned.

Focused route acceptance: `npx vitest run tests/platform-v2-routes.test.ts` and `npm run typecheck`. The route tests cover strict input, shared GET/POST limits, slot retention, sanitized failures, and exact decimal serialization. The local Anvil/HostKit fixture in `tests/platform-v2-durable-bridge.test.ts` rejects relabeled v1 financial evidence. `tests/platform-v2-issuance.test.ts` exercises actual opt-in issuance, both configured copies and canonical public HTTP retrieval after restart. `tests/platform-main.test.ts` checks actual server mounting without a wallet session and the inherited origin gate. These local tests do not supply a funded public wallet, an archive-capable Base RPC, or independently reviewed live immutable evidence stores.
