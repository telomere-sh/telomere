# Platform financial receipts

`PlatformReceiptService` in `src/receipts/platform-service.ts` implements the runtime's owner-scoped `record`, `publishClosed`, and `proof` port. Its separate tables/DDL are exported by `platform-schema.ts`; standalone callers can call `initialize()`. Configure the exact chain, escrow and receipt-root addresses, a viem public client, and the runtime's durable `PlatformTransactions.submit` callback. Production callers must supply `canSeal(hour)` to block any admitted reservation whose outcome for that hour is unknown. The runtime serializes job admission, completion and publication around that guard.

The guard must also require `hasRecorded(owner, settlement)` for each relevant nonfinal financial outcome: a settlement JSON already stored in the job does not mean a bounded drain pass inserted it into this financial tree. For example, processing 32 of 33 completed outcomes must keep the hour unsealed until the 33rd immutable entry is present. Entries cannot be deleted to bypass this guard.

The financial leaf is **not** the legacy receipt-hash-only leaf. `platformFinancialLeaf` independently double-keccak hashes ABI encoding of `uint256 chainId`, `address escrow`, `bytes32 runId`, `bytes32 hostId`, `address payer`, `uint16 hwClass`, `bytes32 regionHash`, `bytes32 imageHash`, `bytes32 workloadHash`, `uint64 billableSeconds`, `uint64 endedAt`, `uint96 inferenceCharge`, and `bytes32 receiptHash`, in that order. It matches `PlatformRunEscrow.receiptLeaf`. The generic helper supports inference charges; this runtime service admits the currently implemented CPU path with inference zero. Sorted pairs and odd-node promotion match OpenZeppelin MerkleProof.

`record(owner, settlement)` reads the canonical on-chain reservation and Leash, checks payer, active reservation, stop/kill/expiry cutoffs, maximum and elapsed seconds, refund deadline and receipt replay, then compares the independent leaf with the contract helper. Persisted entries are immutable and ordered by run ID when sealing. An hour must be closed according to chain time, contain at most 4096 entries and pass the runtime's pending-outcome guard. A late outcome for an already sealed hour raises `platform_receipt_late`: its `endedAt` and hour are never shifted. The original reservation needs explicit reconciliation or its independent contract refund. The service neither invents a replacement settlement nor initiates a new customer payment.

`publishClosed()` handles at most 32 pending hours per pass. Batch metadata is committed before dispatch. All root and settlement broadcasts use the runtime's single durable signer nonce journal, with an immutable publication key derived from chain/escrow/root scope and hour. A lost response is recovered by submitting the same journal intent; reorg recovery rebroadcasts identical signed bytes if the original nonce is still available. Consumed or conflicting nonces require reconciliation.

The deployed `ReceiptRoot` accepts `postRoot(hour, root, count)` directly from `SignerSet.currentSigner()`. It has **no EIP-712 root authorization method** and no separate signed epoch payload. Publication uses the actual chain transaction signature. Epoch authorization is checked against `weeklySigner(postedAt / 604800)`; new publications fail closed when the current week has no signer. Platform quotes use the contract's actual EIP-712 `TelomerePlatformEscrow` domain. Root inclusion records the publisher's commitment, not independent computation truth.

Proofs are available only to the entry's owner and only after canonical publication is established. Every response rebuilds the full bounded tree, checks local field/hash/position integrity, verifies actual transaction destination/calldata/chain/sender/value/status/block hash, one exact `RootPosted` event, the actual `getRoot` value/count/signer/time, historical signer epoch and canonical escrow run fields. Cached database metadata alone never establishes on-chain verification. An orphaned, wrong-tree or mismatched publication fails closed. Full runtime bytecode pin review remains the responsibility of `PlatformBridge.check()` before admission.

Local acceptance: `npx vitest run tests/platform-receipts.test.ts`. Tests deploy real contracts on a disposable loopback Anvil chain with generated accounts, exercise actual quote signatures, root publication, full-proof settlement, nonce persistence, PGlite disk reopen, ambiguous-response recovery, reorg rollback/rebroadcast, field tampering, late outcomes, owner isolation and unscheduled signer epochs. No public-network transactions or paid provider calls are involved.
