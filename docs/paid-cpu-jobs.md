# Paid CPU jobs and replacement

The mounted Vault API supports durable owner-approved CPU jobs over the reviewed HostKit catalogue. A job retains its original Vault, workload, allowed lanes, deadline and fee-inclusive total budget. It prepares unsigned quotes; funding and admission require the owner's external wallet flow. The active settlement target is Base/native USDC. Local acceptance uses disposable Anvil contracts.

## Owner API

All paths below are relative to `/api/platform/vaults/:vault/cpu-jobs`. The authenticated human Vault owner is required for job creation, observation, approval and cancellation. An agent's compute credential alone cannot approve a new interruptible policy.

| Method and suffix | Action |
| --- | --- |
| `POST /` | Create the immutable job and initial quote; requires its original `Idempotency-Key`. |
| `GET /:id` | Read original intent, current quote, canonical charges and full outstanding liabilities. |
| `POST /:id/replan` | Propose replacement after canonical source settlement and retained HostKit cleanup; requires its original operation key. |
| `POST /:id/approve` | Approve the exact current `decisionHash` and prepare a separate replacement quote. |
| `POST /:id/cancel` | Fence new work and request controller watchdog shutdown; retain liabilities until final settlement/refund. |
| `POST /:id/finish` | Finish only after all original reservations settle and current source cleanup is retained. |
| `GET /reliability/:hostId/:lane` | Read explicitly scoped thirty-day CPU history and sample counts. |

Creation uses protocol `telomere-paid-cpu-job-v1`, the original `leashId`, a reviewed session task, `workSeconds` from 10 to 120, deadline, total `maxSpend`, allowed regions and lanes. Including `interruptible` requires `interruptibleConsent:{minimumNoticeSeconds:30}` and more than 30 seconds of work. Replanning supplies the owner-held checkpoint's hash, remaining original work seconds and restore seconds; their sum must fit a separately funded 10 to 120 second reservation. A job retains at most 64 original reservations. These limits do not describe an unbounded batch scheduler.

Replanning also accepts optional `expectedSourceRunId`. Owner-side background operations supply their retained source ID so a delayed request cannot replan or cancel a successor. The server checks this before deadline cancellation and uses its existing revision compare-and-set for later writes. An exact same-key replay retains the original request semantics and returns the current job view; callers must recognize a successor rather than interpreting that response as the old proposal. Existing callers omitting this field retain their previous behavior.

Finishing accepts `{expectedSourceRunId}` as an optional original-source fence. It is checked before even the already-finished replay, so a delayed completion cannot finish or adopt a successor. Node `finishCpuJob(jobId,{expectedSourceRunId})`, Python `finish_cpu_job(job_id,expected_source_run_id=...)` and MCP `telomere_paid_cpu_job_finish` carry that same field. The existing omitted field or empty body remains supported for direct owner calls. Finishing still requires the authenticated human owner, canonical source settlement, retained original HostKit cleanup and zero outstanding job liabilities.

Node `PlatformVaultRuntimeClient` exposes `createCpuJob`, `cpuJob`, `replanCpuJob`, `approveCpuJob`, `cancelCpuJob`, `finishCpuJob` and `cpuReliability`. The Python Vault client exposes the corresponding snake_case methods. Mounted MCP tools have the `telomere_paid_cpu_job_` prefix, plus `telomere_paid_cpu_reliability`. None of those job operations broadcasts a wallet transaction or uploads application plaintext.

## Signed authority and accounting

The optional versioned `cpuScheduling` commitment binds the lane, owner consent and original job reference into the financial workload hash and paid HostKit lease. Omission preserves the earlier standard-lane hash. Interruptible admission requires an explicitly reviewed host capability and durable exact-lease HostKit opt-in before commands or billable ACKs. A host must give at least 30 seconds' signed notice; an arbitrary quote field cannot create that authority.

A replacement proposal binds the source quote, actual confirmed charge/refund, retained cleanup, checkpoint commitment, original deadline/budget, restore duration and exact target offer. The owner approves that decision hash. The service then rechecks eligibility, price and full liabilities before creating a new immutable quote. Already charged amounts and every pending reservation count against the original total budget. Pending refunds are not available funding. Deadline or capacity failure can cancel the job; its existing liabilities remain visible and require the original canonical financial outcome.

The owner obtains the prepared plan through the existing checked Vault SDK, executes it externally, records the transaction and admits the original quote. Application checkpoint capture and restoration use the existing owner-side handoff protocol. Proposal creation or approval does not execute those steps. Lost API responses reuse retained job/decision identities rather than replacing approved terms.

## Owner-side automatic replanning

`PaidCpuJobReplanRunner` joins the previously separate capture, wait and replan steps for one original interruptible CPU source. The owner supplies the original active job snapshot, remaining application work, estimated restore duration, checked owner client, existing `PaidPreemptionHandoff` and durable `PaidLifecycleClientVault` or V3 journal. Retain that original snapshot and those estimates across restart; constructing a new cycle from a later successor would create a different operation.

The journal scope uses `PAID_CPU_JOB_REPLAN_SCHEMA`, with the original owner and agent wallet. `runOnce()` or `tick()` advances one cycle. Explicit `watch({signal,pollMs})` polls sequentially, with a default one-second interval and a supported range of 100–5,000 ms. It returns once a proposal requires owner approval, the original job is cancelled, or a successor supersedes this source. The embedding owner stops this preemption watcher on ordinary application completion and uses the existing job finish flow. Aborting wakes the polling wait and drains an in-flight cycle before returning; it does not cancel an approved successor.

The runner checks the retained job, chain pins and source, waits for a signed notice, and invokes the existing idempotent application checkpoint hook. Immutable encrypted records retain the original operation, notice, capture and exact replacement request under an exclusive owner operation lock. Unsettled source charges or any outstanding original liability keep the cycle waiting. After canonical settlement, one deterministic request carries the checkpoint commitment and `expectedSourceRunId`. Lost responses reconcile that original key before the runner accepts a proposal. Changing work estimates, checkpoint identity or original bindings refuses the old operation.

`waiting_notice` means only the reviewed host's exact missing-notice response. Other transport, signature, journal or policy errors remain errors. `awaiting_owner` returns the replacement proposal for its existing explicit decision-hash approval and external funding flow. The runner has no approval, payment, admission, stop or restore port; HostKit's existing signed-notice watchdog enforces source shutdown. It operates on the bounded CPU catalogue and the existing small application checkpoint path. Large filesystem export, automatic funding and independent physical-host recovery retain their separate requirements.

## Explicit owner completion

`PaidCpuJobFinishRunner` finishes one original source after an explicit owner/application declaration. Its constructor receives the original active job snapshot, `applicationCompletionHash`, the checked owner client and a private lifecycle journal scoped with `PAID_CPU_JOB_FINISH_SCHEMA`. The hash is the owner's opaque declaration of completed application work; financial settlement, wall-clock seconds, a cancelled CPU result or a host's assertion never create this declaration. Retain the same snapshot and declaration across restart. For an interruptible application, the embedding owner first aborts its preemption watcher, then starts this separate completion runner.

`runOnce()` or `tick()` advances one cycle; explicit `watch({signal,pollMs})` waits sequentially at 100–5,000 ms intervals, defaulting to one second. The encrypted immutable journal binds the original job intent, source quote, Vault, owner, agent and application declaration. After original financial settlement and zero liabilities, it retains the exact source-fenced request before sending the existing finish operation. The server independently confirms canonical accounting and original cleanup. Uncertain accounting or cleanup returns `waiting_source`; a cancellation or successor terminates the cycle without changing that job. A lost response reuses the original source fence after journal reopen. An unrelated manually finished job is not adopted when the runner has no retained request.

The runner exposes only config, job observation, original source observation and finish ports. It cannot stop an application, issue a refund, approve or fund a successor, admit work or broadcast a wallet transaction. Abort wakes the poll and drains an in-flight finish; it does not undo a committed completion or cancel a successor. This closes owner-side completion orchestration for the existing bounded CPU job; it does not add automatic public funding, supplier execution or a long-running batch scheduler. The earlier frozen replan acceptance above remains scoped to its original source cutoff; later finish checks are separate.

## Reliability boundary

Selection reads a thirty-day window of canonical financial settlements accompanied by retained controller/HostKit cleanup evidence. Observations are scoped to the exact CPU host and original lane. The response exposes eligible/completed counts, excluded unverifiable records and the explicit neutral no-history prior. This is local verified history, not a market-wide quality measurement or hardware attestation. Only actually admitted reviewed supply participates; absent GPU or external-supplier prices are not invented.

The focused 15 October cohort passed 37 cases across paid jobs, consent/reliability and interruptible orchestration. Its paid job case used real local-EVM Vault payments, a signed host notice, encrypted checkpoint, canonical old-run settlement, exact owner approval, separately funded standard-lane replacement and response-loss recovery. It also paid an already cancelled quote externally before its expiry and proved zero dispatch with full liability retained until canonical refund. This does not establish separate physical-host failure recovery, a production fleet or funded public Base acceptance.
