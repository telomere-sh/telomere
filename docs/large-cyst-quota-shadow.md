# Quota shadow for two remote large-Cyst copies

`LargeCystQuotaShadowStore` composes an existing `LargeCystPrivateStore` with two managed `LargeCystStore` destinations. The local private store is a full third ciphertext copy. It remains the authority for the existing per-owner/global byte caps and the 32-per-owner/4096-global checkpoint-ID caps. It never receives the recovery key or plaintext. Each operation first records its immutable header, part or manifest locally, then writes the two remote copies. A failed remote write keeps the local bytes and their quota reservation; it cannot create an uncharged remote object through this coordinator.

The original local part is returned during an interrupted upload. This matters because owner-side encryption generates a random nonce: if both remote part writes fail, regenerating ciphertext for the same source would conflict with an already reserved local part. After restart, the owner can read that original part or call `repair(id)` after a local manifest exists. Remote reconciliation copies only confirmed missing parts from the local shadow; it checks existing part digests and refuses to overwrite corrupt or conflicting immutable objects. A small immutable local intent file reserves the exact proof quota before publishing either remote manifest; it survives a crash between remote commit and local seal. A remote manifest is acknowledged only after both destinations and all their parts pass `LargeCystReplicatedStore.isDurable`, then the intent atomically becomes the committed marker. A local-only or single-remote manifest stays pending through restart. The marker lets later manifest reads avoid re-downloading up to 4 GiB of remote parts for a 2 GiB checkpoint. `isDurable(id)` remains the explicit live two-copy audit. A previously committed manifest remains available during one provider outage; part reads use the local ciphertext and can fall back to a digest-verified healthy remote copy if the local part is missing or corrupt.

The component serializes writes per checkpoint ID and uses the private store's existing writer lock. The optional main-server factory parses a strict private S3 configuration whose exact bytes are pinned by `CYSTS_LARGE_REPLICATION_CONFIG_SHA256`. It rejects identical endpoint origins, region names and failure-domain labels. The local store immutably binds its directory to the reviewed redacted destination topology, after both S3 startup probes pass. A first boot with either destination unavailable fails without creating the topology binding. A later boot with the same binding can start read-only if a destination is unavailable: previously sealed manifests and local parts can be restored, `isDurable` reports false because the live two-copy audit is unavailable, and all checkpoint writes and repairs fail closed. `/api/config` exposes `largeCystsWritable=false` and the server logs `large_cysts_read_only_remote_unavailable`. Restart after restoring both destinations to resume writes. A restart with different destinations, a silent switch back to local-only mode, or switching a nonempty legacy local directory to remote mode fails startup. Credentials can rotate without changing the topology binding, but the config file hash must be updated. These checks do not prove geographic or operational separation: labels alone are insufficient, and no external provider has been contacted by this implementation or its tests. Migrating a legacy local store or changing destinations requires an offline, verified operator procedure.

The local full copy preserves crash accounting at the cost of additional disk and write I/O. Byte caps count logical ciphertext payload stored in the local shadow; each S3 destination needs its own capacity and billing controls. Successful retries and commits can require another full read of remote parts. The 2 GiB transfer target and sustained provider behavior remain unverified. There is no online deletion or quota release; retention and offline cleanup require an operator procedure while writers are stopped. The focused local tests cover remote failure before any part reaches a destination, restart and retry, partial commit, durable repair, concurrent conflicting writes, checkpoint count and byte caps.
