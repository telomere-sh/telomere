# Large Cyst publication jobs

Current network target: Base 8453 / Base Sepolia 84532 with native USDC. Dated acceptance and linked JSON evidence retain their original network/source scope; see [migration record](base-usdc-migration-2026-10-14.md).

The large-file CystRegistry publication boundary is an authenticated **unsigned** asynchronous job. It is mounted at `/api/cysts-large-registry` only when the controller has both a reviewed, SHA-256-pinned two-destination S3 replication configuration and a reviewed pinned CystRegistry reader. An unconfigured or startup-degraded remote pair leaves these routes unmounted. The controller never signs, broadcasts, stores, or receives a recovery key.

The Selection agent wallet signs into the normal Telomere session, then sends `POST /api/cysts-large-registry/agents/:agentId/jobs` with `Idempotency-Key`, JSON `{"checkpointId":"0x..."}`, and the normal same-origin header. The agent wallet must equal the original canonical Selection `agentWallet`; in either public Base mode that wallet must also be included in `PILOT_ALLOWED_OWNERS` so it can create a session. The response is `202` with a durable job ID and status. The same wallet polls `GET /api/cysts-large-registry/agents/:agentId/jobs/:jobId`; it may send `POST .../:jobId/cancel` with JSON `{}`. Other wallets cannot read a job. The input body is capped at 512 bytes with a five-second read deadline. Eight queued/running jobs are allowed globally, at most one queued/running audit per agent, with a single audit worker and a 30-minute per-job deadline. A duplicate idempotency key returns the original job only for the same agent and checkpoint after admission; at capacity the caller receives 429 and can retry the same key.

Jobs are stored in the controller database. After an unclean crash, the operator must first recover the local shadow's stale writer lock using its reviewed PID-proof procedure; startup then requeues interrupted unsigned scans and honors saved cancellations. A completed result is an unsigned `commitChecked` transaction tied to the original Selection binding and current CystRegistry revision. Retrieval rechecks canonical binding/state; it discards calldata after a state change or five minutes. The onchain expected-revision argument makes a stale transaction revert even if the state changes between retrieval and signing.

The single-controller worker reads and hashes every required ciphertext part in **both** configured destinations through `LargeCystRegistryPlanner`. No more than eight submissions may wait on admission checks in memory; the database separately caps queued/running jobs at eight. Cancellation and the absolute job deadline propagate into each signed S3 GET and its response stream; the worker waits for the scan to finish or abort before admitting another. The final success update also checks the database deadline atomically, and `/health/ready` fails if the queue stops unexpectedly. Each remote request retains its 10-second individual timeout. A failed, unavailable, altered, or incomplete copy does not produce calldata. The worker checks the immutable manifest and canonical chain state again after the scan.

Before signing, the agent-side `checkedLargeCystCommitPlan` independently reads the original manifest with `LargeCystAgentManifestStore`, verifies its owner-keyed MAC with the recovery key, checks the reviewed CystRegistry pins and current canonical state, and reconstructs exact `commitChecked` calldata. When the manifest includes a wrapped key, the agent must supply its own X25519 identity: the checked client unwraps the agent recipient and proves it equals the authenticated recovery key before returning calldata. The checked client refuses to return signable calldata for a mixed owner/agent bundle or an unrecognized agent recipient key. The raw planner output remains unsigned calldata and does not enforce this client-side key check. The read-only `GET /api/cysts-large-registry/agents/:agentId/checkpoints/:checkpointId/manifest` accepts only a signed session for the original canonical Selection agent wallet and requires the committed manifest header's owner and agent to match the canonical binding. The response is uncached and limited to 128 KiB. The SDK fetcher enforces status, headers, byte limit, schema, and checkpoint ID; the manifest's MAC is authenticated by `checkedLargeCystCommitPlan`, not by trusting the HTTP response. It returns the validated unsigned transaction to the wallet. The recovery key stays on the agent side and the function clears its temporary copy. The controller's existing large-Cyst upload/download HTTP routes remain owner-only. Agents should restore the checkpoint with their recovery key before publishing if they need proof that its plaintext is usable.

For checkpoints whose owner saved an optional wrapped-key bundle in the immutable manifest, the same signed agent session can now read ciphertext through `GET /api/cysts-large-registry/agents/:agentId/checkpoints/:checkpointId/parts/:index`. The server checks the original live agent binding before and after the read, validates the part against the committed manifest SHA-256, and limits active transfers to four. A part read has a 20-second backend deadline and releases its slot even if a store fails to honor abort. The response is binary, uncached and bounded by the manifest's 4 MiB part length; a stalled transfer closes after 60 seconds. `LargeCystAgentManifestStore` checks response headers, exact length and digest independently. `restoreLargeCystFileWithWrappedKey` unwraps only the selected owner or agent recipient, checks the owner-keyed manifest MAC, restores into a private temporary file, and clears the recovered key. This helper restores the requested checkpoint ID; a caller claiming the **current onchain revision** must additionally compare the manifest descriptor with a fresh canonical CystRegistry read. The owner upload path remains separate. Agent restoration still needs a configured replicated store, a valid agent session and an X25519 private identity retained outside the controller.

The signed original agent may resolve its **current** onchain locator with `GET /api/cysts-large-registry/agents/:agentId/checkpoints/current`. A separate descriptor catalog is written atomically when a two-copy publication audit succeeds. It retains the checkpoint ID, full immutable descriptor, original Selection identity and reviewed registry deployment after the short-lived unsigned job plan expires. Resolution first reads the confirmed canonical CystRegistry state and looks up that agent's current `storageRef`; it returns a checkpoint ID and original manifest only when the catalog, owner/agent binding, `cystHash`, size, `storageRef`, and recomputed manifest descriptor all match. A second canonical read rejects a changed revision, binding, or same-height block hash. The JSON response is uncached and capped at 144 KiB. `LargeCystAgentManifestStore.resolveCurrent(reader)` independently validates that response against the manifest and a separately pinned canonical reader. Its `restoreCurrent` method then verifies the wrapped key and full plaintext, rechecks the pinned canonical binding and revision immediately before atomic destination publication, and removes temporary plaintext if the state changed during download. Callers that use `resolveCurrent` with the lower-level `restoreLargeCystFileWithWrappedKey` must perform that final canonical check themselves. A later chain change can still make any completed restore historical. The server cannot verify the owner-keyed manifest MAC or prove the plaintext is usable; the agent's unwrap and restore check those properties.

The catalog is a locator for checkpoints audited through this controller, not a global onchain index. A checkpoint committed directly or audited before the catalog migration has no entry and fails closed until its offchain ID is supplied for a new audit. A merely successful audit does not imply an onchain commit; the current route stays unavailable until the registry actually points to its exact descriptor. Missing, stale, reorged or corrupt catalog evidence never selects a historical checkpoint, and this endpoint exposes no recovery key or S3 credentials.

This local implementation does not establish independent cloud-region failure domains, a public Base transaction, source-verified deployment, or end-to-end 2 GiB timing. Production rollout still requires those separate acceptance gates.
