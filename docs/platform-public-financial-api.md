# Public Platform financial reads

Current network target: Base 8453 / Base Sepolia 84532 with native USDC. Dated acceptance and linked JSON evidence retain their original network/source scope; see [migration record](base-usdc-migration-2026-10-14.md).

When the reviewed `PLATFORM_RUNTIME_CONFIG` is enabled, the main server mounts four unauthenticated, read-only JSON routes. The financial routes do not read `platform_runs` or the receipt database; none of these routes sign, broadcast, reserve funds or claim that CPU work was performed correctly. They use the configured RPC and reviewed Platform pins. The application limits this public namespace to six requests per socket IP per minute; refund and price-window scans are each serialized in one process.

`GET /api/platform/public/receipts/{runId}?transactionHash={txHash}` independently reads the supplied canonical settlement or timeout-refund transaction. The transaction hash is **required**: the current reader does not search unbounded chain history by run ID. For a settlement, it decodes `settleRun` or `settleBatch` calldata, finds exactly one matching run, recalculates the full financial leaf, checks its proof against the published `ReceiptRoot`, reads the escrow's final run state, and checks the `RunSettled` event against exact host amount, rounded platform fee and returned reservation. A timeout refund requires a successful `refundRun` call, final escrow state and the exact `RunRefunded` event. Both paths check the chain and current deployment pins, historical USDC proxy/implementation/facet pins at the transaction block, historical escrow/root/router code, canonical block hash and at least twelve block confirmations. A reorg, missing archive state or changed pin fails closed. The response says `verification: "chain-financial-only"` and `tickSignaturesVerified: false` on purpose.

`GET /api/platform/public/refund-rate` reads the latest 256 finalized blocks. The optional `fromBlock` and `toBlock` decimal parameters must be supplied together and cover at most 256 blocks within the latest 65,536. This is a **finalization-event window**, not an opened-run cohort. `timeoutRefundRateBps` is `RunRefunded / (RunRefunded + RunSettled) × 10,000`, rounded down, and is `null` when the window contains no finalizations. A successful settlement's unused ceiling returned to the payer is not counted as a timeout refund. The reader checks canonical event blocks and historical pinned contract code; it rejects duplicate run IDs and windows over 512 events. The response includes exact bounds and the canonical end-block hash so a dashboard can label its coverage. This route provides backend JSON, not a hosted dashboard.

`GET /api/platform/public/cpu-price-board` returns `p10`, median and `p90` of the **signed host quote's onchain `pricePerSecond`**, in integer micro-USDC per billable CPU second before the platform fee. The median can end in `.5` micro-USDC for an even sample; p10 and p90 use nearest-rank order statistics. The fixed windows are `(finalized anchor block timestamp − 1 hour, anchor]`, `(anchor − 24 hours, anchor]` and `(anchor − 7 days, anchor]`. The scan requests every `RunSettled` event in the seven-day finalized block window and rechecks each returned event with the financial reader's canonical transaction, historical contract/asset pins, final escrow state, receipt-root Merkle proof and exact amount conservation. It then includes only runs with `hwClass = 0`, unsealed host, positive billable seconds, positive unit price and **zero actual inference charge**. Mixed CPU+NEAR settlements are intentionally excluded from this comparable CPU-only sample, even though their CPU unit price remains onchain. Timeout refunds, zero-second inference-only requests and other classes are excluded. An empty window has count `0` and null quantiles.

The response names its coverage `restricted-reviewed-platform-cpu-unsealed-settlements`, sets `marketWide: false`, `standardLaneOnchainVerified: false` and `rpcLogEnumerationAssumed: true`, and reports verified event and eligible-sample counts. The reviewed controller currently offers only the `standard` CPU lane, but the escrow does not record a lane; this route cannot independently prove historical lane assignment or prices across other suppliers. It depends on the configured RPC to enumerate all matching logs; verifying each returned log does not prove the RPC omitted none. Its existing financial verifier accepts direct escrow settlement calldata; a contract-mediated settlement event in the window makes the entire board unavailable instead of being silently skipped. At most 1,048,576 finalized blocks, 128 settlement events, 8,192-block log chunks and a 30-second response budget are allowed. If a chain is denser, a log or proof cannot be verified, historical state is unavailable, or the anchor reorgs, the route returns an error and **no partial seven-day percentile**. One in-flight read per process is allowed; a timed-out read retains the lock until its pending bounded RPC call exits. This is a restricted pilot backend feed, not a complete M8 public marketplace board. The existing `/api/jobs/prices`, SDK `prices()` and MCP `telomere_price_board` still use the separate legacy controller-local job samples, not this Platform chain feed.

`POST /api/platform/public/presented-meter/verify` accepts a caller-supplied bounded bundle of signed HostKit ticks and verifies their signatures against the historical onchain `HostRegistry.hostKey` for the canonical paid run. It exposes the same narrow result as the [read-only offline tool](platform-presented-host-ticks.md): `completeTickHistoryVerified`, `billableSecondsVerifiedFromTicks` and `onchainTickCommitment` are all `false`. The v1 receipt does not commit the complete signed tick/ACK set, and this endpoint neither retrieves missing evidence nor certifies controller ACKs. The shared API middleware requires the configured `Origin` and JSON content type for POST; the route has a 96 KiB body bound and stores no submitted bundle.

The original public `GET /receipts/{run_id}` gate requires a complete, publicly committed HostKit tick/ACK history and a hosted proof for it. The present financial route and presented-tick route are narrower. A root inclusion proof shows the authorized publisher committed a financial leaf; it does not prove the host performed the claimed CPU work. Before live Base acceptance, deploy and independently verify the final contract/asset pins, provide an archive-capable RPC and funded owner transactions, test real public settlement/refund and reorg handling, add an immutable privacy-preserving signed-meter commitment with durable public evidence, and test the public URL/dashboard under operational load. The Anvil tests in `tests/platform-public-financial.test.ts` and `tests/platform-presented-meter.test.ts` cover the narrower routes with real local transactions only.
