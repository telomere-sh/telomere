# Akash direct-chain spend boundary: feasibility, 14 October 2026

The current Telomere signed Akash path uses the managed Console API and deliberately stops before a paid lease POST. Its selected BidID/unit-price check does not bind a maximum lifetime USDG cost. Console can fund deployments from account credits, and its per-deployment `autoTopUpEnabled: false` setting is not accepted by the path we checked. A finite prepaid Console account would bound aggregate cash available to Console, but would not atomically reserve one Telomere run's maximum supplier obligation.

A separate **self-custody direct-chain** design may bound the amount of ACT that can actually leave a deployment escrow: create one deployment with an exact initial `uact` deposit at or below an approved supplier reserve, create exactly one lease for the verified BidID, use a dedicated signer without grants or automatic top-ups, and never add funds to that deployment. Akash documents deployment funding, escrow drawdown, closure when funds deplete, and refund of unused escrow. `MsgCreateLease` fixes the BidID and unit price; it has no lifetime-cost field. A separate, bounded AKT balance is needed for transaction gas. The Console `runtimeLimitHours` minimum is a Console API condition, not a direct-chain lease minimum; direct deployments can be explicitly closed.

**This is a cash-outlay bound, not yet an enforceable total liability bound.** Akash's escrow implementation can record negative funds and `Payment.Unsettled` when usage overdraws a deployment; a zero escrow balance therefore does not itself prove that the provider's accrued claim is zero. The direct-chain route also does not atomically bind Akash identity, precision/denomination, exchange rate, the Telomere USDG reservation or the current 120-second CPU quote. It cannot enable paid Telomere admission on the strength of the deposit alone.

Before any paid integration, independently review the exact chain version and overdraw semantics; require a provider agreement or protocol mechanism that caps accrued obligation, not just spendable escrow; bind the selected bid, deposit and maximum time to the admitted Telomere quote; support the selected bid's actual denomination (fractional `uact` planning is now supported locally); use an isolated funded account; verify deployment/lease/heartbeat/close and final escrow, unsettled debt, refunds and FX against a funded run. Keep the existing `supplier_atomic_budget_unavailable` refusal until these checks pass.
