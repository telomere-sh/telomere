# Paid interactive CPU Cells

Current network target: Base 8453 / Base Sepolia 84532 with native USDC. Dated acceptance and linked JSON evidence retain their original network/source scope; see [migration record](base-usdc-migration-2026-10-14.md).

The platform backend can quote an interactive `session` task on an explicitly reviewed CPU host. This is a bounded, paid Cell: one process persists across up to 32 sequential commands, with a quoted lifetime of 10–120 seconds. The lower bound leaves time for authenticated host admission before the host's five-second lease-expiry guard. The quoted task is `{ "kind": "session", "imageDigest": "sha256:…", "maxCommands": 4 }`. Its image digest and command limit are covered by `workloadHash` in the platform-signed quote submitted by the owner or Vault agent. A host must opt in with `sessionEnabled: true`, carry that exact image, and run the shared Host Kit session manager on gVisor or Kata. The local process backend is a test fixture only.

The owner first creates an active CPU Leash and funds the original escrow or Vault. `POST /api/platform/quotes` returns the exact wallet transaction plan. Only a canonical, successful `openRun` receipt accepted by `POST /api/platform/runs` queues the Cell. The controller checks the live run, Leash, deadline, host key, image, and Vault policy before dispatch. It then signs one fixed-policy Host Kit session lease containing the quote hash and admission transaction. The host trusts its configured controller key; it does not infer payment from a client-supplied claim. A failed or unconfirmed admission does not start work.

For an EOA run, the authenticated owner sends a command to `POST /api/platform/runs/:id/commands` with an `Idempotency-Key` equal to the command's `commandId`. The strict JSON body is `{ "commandId": "step1", "argv": ["/path/in/image", "arg"], "stdin": "optional" }`. Retrying the same ID and input returns the original durable command result; changing the input under that ID is rejected. `GET /api/platform/runs/:id/events?after=-1&limit=8` returns ordered, bounded event pages. `PlatformRuntimeClient.command()` and `sessionEvents()` provide the same operations in the Node SDK.

For a funded Vault run, use `/api/platform/vaults/:vault/runs/:id/commands` and `/events`, or `PlatformVaultRuntimeClient`. Only the approved agent wallet can submit a command. The owner and agent can read events; the owner can request a stop. A third-party wallet cannot access the run. A frozen or killed Vault/Leash prevents new command admission.

The fixed policy is one CPU, 256 MiB memory, 64 PIDs, 16 MiB temporary storage, a read-only root and no network. Each command accepts bounded argv and at most 8 KiB UTF-8 stdin. Output is capped at 16 KiB per command and 64 KiB per session. Node and Python clients recheck the current reviewed capacity before exposing an unsigned payment plan, validate command/event responses, and allow 130 seconds for a legitimate 120-second command response. If a response is uncertain, retry the exact command ID and input, then inspect its events and financial run. The financial MCP endpoint exposes the same command and event controls.

The host samples a signed meter roughly every five seconds. The controller validates each tick, persists the tick and signed ACK before sending the ACK, and charges only consecutive intervals with fresh guest heartbeat evidence. The host stops on lease expiry, missed ACKs, faults, or an owner stop. After verified physical cleanup, the controller stores the ordered session event history and its digest in the run result. The receipt commits that digest and the conservative settled seconds. The existing closed-hour receipt root, fee calculation, escrow settlement, refund, and Vault burn then apply. If cleanup or signed evidence is uncertain, the run stays in recovery and no receipt is finalized. Recovery uses the original signed lease and persisted ACK pairs; it never dispatches a command again.

An identical command can also be retried after cleanup or settlement while the original host journal is available. The host reads the retained result without reopening the Cell and signs the full history digest. The controller checks the original lease, stored events and financial receipt before returning that result. A reused ID with changed input conflicts; a new command after expiry remains forbidden. If the original host journal is unavailable, the controller fails closed instead of reconstructing an unproven command response. Host and controller must run the same paid-session protocol revision because the signed status includes the full event-history digest.

Automated acceptance uses real local contracts, an authenticated HTTP API and Node SDK, PGlite journals, signed Host Kit control traffic, and a local process fixture. It covers EOA and funded Vault command access, meter-to-receipt settlement, refunds, host release, event-history tampering, concurrent ACK/stop, and controller recovery. An isolated [private VPS gVisor acceptance](platform-paid-gvisor-validation.json) then ran two authenticated commands in the same real container, paired four signed host ticks with four controller ACKs, physically removed the Cell, and settled the local-chain receipt. The source archive and disposable acceptance script are identified by SHA-256 in the report. This does not establish Base Chain or live-wallet acceptance, a production Host Kit deployment, GPU operation, or NEAR attestation. No 15-minute paid-session promise is made by this 120-second contract and host policy.
