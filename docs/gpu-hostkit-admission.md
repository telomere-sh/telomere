# Default-off GPU HostKit admission seam

`src/host-kit/gpu-admission.ts` connects the existing GPU inventory/class/memory checks to a trusted workload-Cell handle. It is exported from HostKit but is **not mounted in the API, scheduler, platform quotes or paid settlement**. No reviewed GPU runtime implementation is configured, and this code does not make GPU capacity available.

The constructor pins one physical GPU UUID, exact workload image digest, gVisor nvproxy or Kata GPU isolation mode, and the SHA-256 of the canonical GPU class policy. Those values and the run request are copied/frozen; the runtime binding is rechecked at start. The admission probe driver must bind the same UUID, isolation and policy-pinned probe image. `start()` obtains the durable exclusive GPU claim before asking the runtime to create a workload Cell. It refuses a returned handle whose run ID, physical UUID, image, isolation or Cell ID differs, or whose claimed start timestamp precedes this dispatch. An ambiguous runtime start, including a ten-second timeout, or an unverified handle, leaves the claim in place for operator reconciliation. A scalar start timestamp is not proof of a Cell start; a production runtime must derive it from an independently inspected, exact-ID start event.

The admission driver can run only class and memory probes in disposable probe Cells. The warm probe is a separate `GpuHostCell.runWarmProbe()` method on the **same handle** that owns the workload. Its `probeExited` result confirms only the warm kernel/process exited; it does not mean the workload Cell was removed. Runs shorter than 22 seconds are rejected: the first 20 seconds from Cell start are platform-funded, even if the warm probe succeeds sooner, and the final boundary second is conservatively omitted because the local watchdog can begin cleanup at that instant. `GpuHostKitRun.assertBillableSecond()` rejects an interval before warm success, before the end of those 20 seconds, in the future, or ending at or beyond the run limit. This is an additional gate for a future GPU meter, **not a signed meter or financial receipt**. Paired signed GPU ticks, in-Cell heartbeat and host-side physical GPU counters still need implementation and independent acceptance.

`stop()` disables billable eligibility immediately and releases the UUID claim only after the trusted runtime confirms exact Cell removal. Its wait is bounded to ten seconds; an ambiguous stop remains terminal for that run and retains the claim. A local deadline timer calls stop at `startedAt + maxSeconds`; this is defense in depth only. The production runtime **must independently stop the exact Cell by its reviewed maximum** across Node crashes/restarts and inspect absence before confirming cleanup. A failed warm kernel retains the claim for operator review even if Cell cleanup is confirmed; a warm-kernel cleanup ambiguity also retains it. A run rejected before warm due to a stale start can release its claim after confirmed Cell cleanup. The claim cannot be silently reused after a process crash. Host strikes, on-chain penalties and delisting are not yet connected. A caller-constructed `GpuHostKitRun` is not admission proof for a future financial meter; paid authority requires a durable signed lease and checked physical-meter evidence.

The missing hardware-dependent component is a reviewed Linux runtime that proves exact GPU device assignment, fixed CUDA probe image execution, same-Cell warm probing, actual gVisor nvproxy or Kata isolation, physical GPU sampling, and exact Cell cleanup. Neither the current VPS nor the NEAR model inference API supplies this Telomere Cell runtime. Before enabling quotes, run real concurrent GPU admission, throttling, false-VRAM, restart/cleanup and paid metering acceptance on an actual GPU host.

Local regression: `npx vitest run tests/gpu-admission.test.ts tests/host-kit-gpu-admission.test.ts`. These tests use deterministic fake GPU hardware and Cell handles and therefore do not constitute CUDA/isolation acceptance.
