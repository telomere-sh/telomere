# NEAR GPU CVM path, 13 October 2026

**Decision: the existing Enclave NEAR connection is an attested model-inference provider, not an admitted Telomere GPU Cell host.** This is a read-only capacity and API assessment. It created no CVM, sent no inference POST, changed no service and approved no new attestation policy.

**Pilot scope clarified on 13 October:** Telomere requires both verified NEAR model inference and arbitrary GPU Cell execution. The project has no self-hosted GPU server. The viable hardware route for the latter is therefore a **NEAR-managed custom GPU CVM entitlement**; the private-ML-SDK/BYO-host path below is architectural background, not a resource available to this pilot. Existing model-inference credentials and the public dedicated-model request do not establish that entitlement.

The private VPS still runs Enclave and Telomere staging. Its Enclave profile contains a NEAR inference credential and the direct model/verifier configuration documented in [the live report](near-live-2026-10-13.md). The VPS has Docker, but the read-only inventory found no `/dev/nvidia*`, `/dev/tdx*` or `/dev/kvm`, and no `nvidia-smi`, `dstack-vmm`, `vmm-cli.py`, `dstack`, QEMU or `virsh`. It is a CPU client of externally managed inference; it cannot locally boot a GPU CVM.

The running Enclave source at `/opt/enclave/_backend` confirms the distinction. `apps/api/src/gateway.ts` constructs `DevCvm` with `gatewayMode: "managed-near"`, then injects `createNearInference` with `createNearAttestationVerifier` for the configured model (`boot`, lines 156–188). Its health payload explicitly reports `gatewayKeyCustody: "software"` (lines 292–315). `packages/core/src/cvm.ts` labels the local gateway-session descriptor `gateway-session:<serving image>` and `near-provider:verify-before-inference`; the source comment says those fields describe **software admission, never local hardware** (lines 37–45). `/v1/attestation/quote` exposes this locally signed descriptor and `/v1/session` opens the gateway session; neither endpoint returns the raw GPU host quote. The actual flow is a model attestation GET in `apps/api/src/near-provider.ts` (lines 230–305), Python Intel/NVIDIA appraisal, then one `chat/completions` POST and response-signature GET in `packages/core/src/near-inference.ts` (lines 257–348). `agent-runtime.ts` uses gateway quote/session/infer/settle; the running first-party source has no dstack/VMM or custom-CVM deploy call. Thus Enclave's local `DevCvm.quote()` is not a Telomere GPU Cell quote. The Telomere verified inference adapter was already ported from that Enclave flow; reusing the local gateway descriptor would weaken, not add, Cell attestation.

There are three distinct NEAR paths:

| Path | Documented capability | What is established for this pilot |
| --- | --- | --- |
| [Cloud inference API](https://docs.near.ai/cloud/quickstart) | Model completions and [model/Gateway attestation](https://docs.near.ai/cloud/verification/cloud-api). The [public OpenAPI](https://docs.near.ai/api-reference/openapi.json) currently has no published CVM/GPU/host/instance deployment operation. | Enclave has a credential and historical attested eight-GPU completion; 13 October saved model hardware evidence passed, but the policy expired and Cloud Gateway TCB failed. No custom Cell entitlement follows from this credential. Absence from the public API does not rule out a private enterprise API. |
| [NEAR dedicated deployment](https://near.ai/capabilities/dedicated-deployment) | Reserved model capacity; the published request flow records interest and expressly does not create infrastructure automatically. NEAR's [CVM terms](https://near.ai/terms-of-service) describe separately specified offerings. | No deployed Telomere CVM, GPU allocation, deployment control endpoint or order-specific entitlement has been observed. Commercial permission for a third-party Cell marketplace needs contract review before relying on this route. |
| [NEAR Private ML SDK](https://github.com/nearai/private-ml-sdk) on a host we control | A Docker Compose application inside Intel TDX/NVIDIA confidential GPU CVM through dstack-vmm, with assigned GPU, KMS and a guest quote interface. | This is a viable implementation basis only after provisioning a separate compatible TDX/GPU host and hardened KMS. The SDK's local development KMS is not a production key boundary. |

The BYO path's [documented VMM flow](https://github.com/nearai/private-ml-sdk#using-dstack-vmm-recommended) composes a reviewed app with `--kms`, deploys an exact guest image and GPU slot using `--gpu` or `--ppcie`, and retrieves a TDX quote from inside the guest. These are architecture inputs, **not** commands run on the current VPS. An operator would need to pin the VMM/guest image, Telomere runner and CUDA probe images by exact digest, configure a hardened KMS, and provide a controlled network path for HostKit. A model quote cannot be substituted for that guest's quote.

Before GPU Cell quotes can be enabled, an acceptance run must show all of the following on the exact allocated deployment:

1. A Telomere-controlled workload runs in an isolated GPU Cell with a reviewed image digest and one-tenant-per-GPU fencing. Host inventory, GPU assignment and process cleanup must be independently checked.
2. A fixed-seed CUDA class benchmark, VRAM allocation/readback and first-20-second warm probe run in the required isolation; the warm probe belongs to the exact billable Cell. Failure or uncertain cleanup quarantines the GPU and cannot charge the user.
3. Host-signed GPU meter ticks, controller ACKs, in-Cell heartbeat, receipt binding and conservative USDG settlement pass against a locally funded escrow before any public wallet acceptance.
4. For sealed mode, the **Cell's** fresh Intel quote, event log/runner measurement, recipient public key and NVIDIA GPU evidence pass an independently reviewed policy. The resulting quote-bound Cyst key packet reaches only that Cell. The existing NEAR model policy and TLS signer are not this proof.
5. A supported commercial deployment/control route is identified and its exact resources, API permissions, terms and lifecycle tested. Public Robinhood funding, operational monitoring and recovery remain separate release gates.

Until these gates pass, the `src/gpu` component and any HostKit GPU integration remain default-off. NEAR model inference can continue as a separately admitted provider after its own renewed policy and live acceptance; it does not authorize GPU Cell rental or sealed-key release.

For the managed-CVM route, obtain from NEAR a project-specific deployment/control path and written configuration covering arbitrary Telomere Docker/CUDA workloads, supported GPU/TEE type, exact GPU allocation and tenant isolation, start/stop/cleanup and independent quote retrieval, API identity and quotas, metering evidence, cost/latency/SLA, and permission for Telomere to expose Cells to end users. [NEAR's CVM terms](https://near.ai/terms-of-service) describe Dedicated CVM and Shared CVM Instance configurations only when available under the applicable documentation or Order Form; the [public dedicated-deployment page](https://near.ai/capabilities/dedicated-deployment) reserves capacity for model inference and its request does not provision infrastructure. This is a capability/contract gate, not a request to send credentials or run a paid deployment. Until the concrete control path is supplied, software-only admission tests must not be scored as an operational M4 Cell.
