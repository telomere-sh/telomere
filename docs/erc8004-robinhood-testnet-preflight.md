# ERC-8004 Robinhood testnet read-only preflight

Network update, 14 October 2026: the active implementation targets Base and native Circle USDC. Earlier Robinhood/USDG evidence below remains historical and does not prove Base deployment or funded acceptance. See [the current migration record](base-usdc-migration-2026-10-14.md).

The [ERC-8004 team's registry repository at commit `b9e466c`](https://github.com/erc-8004/erc-8004-contracts/blob/b9e466c250744a7e06b13dff9d3c2844ed64f825/README.md#robinhood-chain-testnet) lists an existing Robinhood Chain Testnet Identity Registry at `0x8004A818BFB912233c491871b3d84c89A494BD9e` and Reputation Registry at `0x8004B663056A597Dffe9eCcC1965A193B7388713`. The team's [upgradeable deployment guide](https://github.com/erc-8004/erc-8004-contracts/blob/b9e466c250744a7e06b13dff9d3c2844ed64f825/UPGRADEABLE_IMPLEMENTATION.md) describes them as UUPS proxies at deterministic CREATE2 addresses. [Robinhood's network guide](https://docs.robinhood.com/chain/connecting/) identifies testnet chain ID `46630`, ETH gas and the rate-limited public RPC. A separate Telomere deployment of the two ERC-8004 registries is therefore not the current launch plan.

`npx tsx scripts/erc8004-testnet-preflight.ts` performs a bounded **read-only** check. It accepts no arguments, wallet or signing key. `ERC8004_READONLY_RPC_URL` can select a private HTTPS provider; the endpoint is omitted from output. The method allowlist is `eth_chainId`, `eth_getBlockByNumber`, `eth_getCode`, `eth_getStorageAt` and `eth_call`, with a ten-second timeout and 256 KiB response limit per request. It pins state calls to one canonical block hash three blocks behind the head, rechecks that block, compares both proxy runtime hashes and their EIP-1967 implementation slots (`0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc`), implementation addresses/code hashes, owners and versions, then checks `Reputation.getIdentityRegistry()` against the Identity proxy. Any candidate pin mismatch fails. A separate known historical block probes archive-state availability. The output always states `publisherEnabled:false` and `readyForPublicPublication:false`. It does not generate an authorized publisher profile.

The [2026-10-13 observation](erc8004-testnet-readonly-preflight-2026-10-13.json) matched the team's proxy addresses at canonical block `134094699` (`0x89d48c54cb39686831d224adfff482cbb2bc5ec98d41d2b959d38be52b7b3bb4`). Both proxy code hashes were `0xd0e45b1d89fa9b6cc7e97c1f155d64180e5c232aaccf9900ef9d4fd738c02b41`. The Identity implementation was `0x7274e874CA62410a93Bd8bf61c69d8045E399c02`, code hash `0xa5f9624ea85e45b3f4b8558581f03bfb3e6cefab278d7bf0500ec9bd065dc16f`; Reputation implementation was `0x16e0FA7f7C56B9a767E34B192B51f921BE31dA34`, code hash `0x38602de97f1bd86f0a4729f7f3c0a78b1d27892e6eb581272cce5504a68fd00b`. Both returned owner `0x547289319C3e6aedB179C0b8e8aF0B5ACd062603` and version `2.0.0`. Reputation linked to the listed Identity proxy. These are observed candidate pins, not an independent bytecode audit or permanent trust in an upgradeable proxy owner.

The public RPC returned unavailable historical state for the earlier canonical block in the probe, so `historicalStateAvailable` is false. It cannot satisfy the publisher's historical death/receipt verification. An archive-capable private Robinhood testnet RPC must pass the historical probe and the separate USDG archive preflight, then survive the actual public acceptance flow. An EIP-1967 proxy hash alone does not detect an implementation upgrade; the default-off runtime now requires implementation address/code pins at source, current and receipt block state. The owner can upgrade these contracts later, and same-block upgrade/rollback is invisible to standard end-of-block reads, so deployment governance or transaction traces plus source-to-bytecode provenance require independent review before enabling publication.

At 2026-10-13 07:56 UTC, the public Blockscout address API reported `is_verified: false` for the [Identity proxy](https://explorer.testnet.chain.robinhood.com/api/v2/addresses/0x8004A818BFB912233c491871b3d84c89A494BD9e), [Reputation proxy](https://explorer.testnet.chain.robinhood.com/api/v2/addresses/0x8004B663056A597Dffe9eCcC1965A193B7388713), [Identity implementation](https://explorer.testnet.chain.robinhood.com/api/v2/addresses/0x7274e874CA62410a93Bd8bf61c69d8045E399c02) and [Reputation implementation](https://explorer.testnet.chain.robinhood.com/api/v2/addresses/0x16e0FA7f7C56B9a767E34B192B51f921BE31dA34). The API returned `is_contract: true` for all four. This is the explorer's current verification status, not proof that the deployed code differs from the published ERC-8004 source.

At 08:25 UTC, [the reproducible comparison](evidence/erc8004-executable-comparison-2026-10-13.json) compiled the official repository at `b9e466c` with solc 0.8.24, OpenZeppelin 5.4.0, Shanghai EVM, optimizer 200 and via-IR. It read both proxy implementation slots and both implementation runtimes at canonical Robinhood testnet block `134145656` (`0x92108eaf67d652a44bfb4fd0946baf4a1e6e04ed1367dde9d348cba793769e9c`), three blocks behind the head, and rechecked that block after the comparison. Both proxy slots still pointed to the expected implementations. The script verified the official source commit's npm lockfile, downloaded the pinned OpenZeppelin archives and the separately pinned solc archive, checked SHA-512 package integrity and matched the installed compiler files and every Solidity import to those archives. The evidence records the source lockfile hash, imported-source hashes and their aggregate digest. The two 32-byte compiler-marked immutable references in each contract are OpenZeppelin UUPS `__self = address(this)` and were replaced with the implementation address. The resulting **executable bytes** matched the RPC and Blockscout byte for byte: 14,421 Identity and 10,438 Reputation bytes. Both 53-byte trailers have the expected Solidity 0.8.24 IPFS/solc CBOR shape, but their metadata hashes differ, so the full runtime does **not** match. The read-only [comparison script](../scripts/erc8004-source-compare.mjs) accepts no key and sends no transaction. This narrows the source-provenance gap but does not independently audit compiler transitive dependencies, proxy upgrade governance, historical state, or the publisher's authorized public transaction flow.

The [official Identity v2 source](https://github.com/erc-8004/erc-8004-contracts/blob/b9e466c250744a7e06b13dff9d3c2844ed64f825/contracts/IdentityRegistryUpgradeable.sol#L52-L80) has `register()` overloads that mint the ERC-721 identity to `msg.sender`; inherited `ownerOf` satisfies `PlatformSelectionRegistry._identity()`. Telomere's `enter` **does not mint**: the human owner must first register an unused identity, then call `enter` from that same owner. `spawn` requires another child identity previously registered to the parent owner. This exact wallet path and identity-to-Selection binding remain unaccepted on public testnet. ERC-8004 `agentWallet` metadata initially equals the registering owner, while Selection's `agentWallet` is supplied separately; matching them requires the [owner-authorized `setAgentWallet` and new-wallet signature](https://eips.ethereum.org/EIPS/eip-8004#identity-registry) if the product relies on that metadata. ERC-721 identities can also transfer: Selection stores the owner at entry and does not automatically follow a later identity transfer. The publisher now blocks new feedback and revokes its own earlier feedback on observed owner drift; the onchain Selection owner itself remains unchanged, so a broader transfer policy is still needed before a permanent identity-to-agent binding is assumed.

The local Anvil publisher tests use a disposable exact-ABI registry fixture. The official proxy discovery and this read-only code observation improve the M9 deployment evidence, but do not establish funded public feedback/revocation, a dedicated authorized publisher, real owner registration, a reviewed upgrade policy, source-to-bytecode audit or production RPC retention. The [ERC-8004 specification](https://eips.ethereum.org/EIPS/eip-8004) defines `getIdentityRegistry`, feedback and revocation interfaces; those live transactions remain the wallet-last acceptance gate.
