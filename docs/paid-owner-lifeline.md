# Owner Lifeline composition, 14 October 2026

`createPaidOwnerLifeline` composes the current-rate Metabolism v2 control client, paid lifecycle runner v2, explicit private journal v3, registered checkpoint cadence and finite owner-approved reservation adapter. It runs in the owner's process. The server does not receive checkpoint recovery keys or a wallet signer. Every CPU lease remains bounded to at most 120 seconds; logical continuation saves application state and starts another separately admitted lease. This does not extend one container's lifetime or migrate its memory.

## Explicit inputs

Supply a checked `PlatformVaultRuntimeClient`, authenticated lifecycle control, immutable deployment/image pins, reviewed checkpoint/restore commands, read-only chain client and durable external stop port. Use `HttpAgentLifecycleControl(transport,{metabolismVersion:2,cystQuotaVersion:2})` and `CystClient(transport,{quotaVersion:2})` with the separately reviewed operator quota policy. The top-level `TelomereClient` forwards both optional versions. Defaults preserve their earlier profiles.

Create separate `PaidLifecycleClientVaultV3` scopes for lifecycle application records, framework compute (`telomere-framework-compute/v1`) and funding (`telomere-paid-lifeline-funding/v1`). A shared private filesystem directory/master key is possible because each exact scope is bound and partitioned independently. Use a separate `CystCheckpointVault` for cadence. Existing in-flight v1 records must finish using their original journal; there is no automatic format migration or deletion.

Create `DurableVaultCompute` with its checked immutable profile and framework journal. Pass it and a complete finite `paidLifelineFundingPolicySchema` approval to the composition factory. The approval binds owner, agent, complete compute-profile hash, image, regions, maximum commands, lease duration, per-reservation ceiling, total reserved units, reservation count and a maximum one-day window. Reservation ceilings include conservative platform fees. Their sum consumes approval even after a refund or a stale target; there is no automatic approval renewal. A policy scope accepts one immutable approval. Rotate it only explicitly after reconciling the old policy and its wallet operations.

The factory returns `{lifeline,reservations,cadence}`. `await lifeline.start()` requires an error callback, performs a first tick and schedules further ticks. `await lifeline.close()` waits for an in-flight operation and stops local polling. It does not kill the agent. An operator can also use `lifeline.tick()` explicitly. The same reviewed private journals and wallet lookup journal must survive process restart.

The reference composition requires explicit quota v2 on both its lifecycle and cadence clients. Immediately before each new broadcast it reads their actual negotiated owner usage and requires room for at least four 4096-byte encrypted captures. With insufficient headroom it returns no new reservation, so a due rollover can checkpoint/sleep. This read is a preflight, not a server-side storage reservation: concurrent uploads remain subject to the server's atomic count/byte checks. Owners must monitor shared usage and stop new work before exhaustion. A slow storage read is followed by a fresh lifecycle/window/quote-expiry check before broadcast.

## External wallet contract

`PaidLifelineFundingPort.submit(plan,operationId,approval)` receives the exact checked Vault calldata and full approval plus policy hash, slot index, ledger hash, cumulative reserved units and original ceiling. A production wallet implementation must independently verify these facts, enforce its finite policy and store the accepted operation and latest policy anchor atomically **before broadcast**. `lookup(operationId)` returns the original transaction hash or null. `anchor(policyHash)` returns its most recent accepted slot index, ledger hash and cumulative reserved units. This port is deliberately supplied by the owner; no automatic production signer is bundled.

The adapter retains input before quoting, exact proposal before budget allocation, full ceiling before submission, and an attempted marker before calling the wallet. A lost acknowledgement with unresolved lookup blocks further funding, including after a mode/version change. It never resubmits an attempted operation. A resolved original transaction is retained before the admission POST; a lost admission response replays the same quote/hash. A wallet anchor newer than the available owner journal blocks new funding until reconciliation, so restoring mixed-age backups cannot quietly reset the local budget. The external wallet must retain and enforce its own policy journal; restoring both journals to an older point is outside the local filesystem's guarantees and remains bounded only by the on-chain Vault/Leash controls.

Lifecycle context, kill state, approval window and quote expiry are checked again before broadcast and before/after admission. A known funded target that became stale is retained as retired and is not admitted merely to make it visible. `reservations.inventory()` includes those original run IDs, transaction hashes and full reserved liabilities. The controller already retains their prepared quote rows and observes canonical timeout refunds through its existing unadmitted-refund recovery. For recovery, the owner can obtain the checked Vault SDK `refundPlan` after the canonical timeout, or `stopPlan` for an admitted run. This composition does not silently sign either recovery action.

## Capacity and state limits

This funding adapter requests standard-lane sessions. The separately mounted M8 paid-job API handles owner-approved interruptible lanes and exact replacement decisions. If one host has no free slot while the source is active, the owner loop can checkpoint/sleep at rollover, then quote and wake after cleanup; it does not claim seamless dual capacity. Unexpected errors fail closed and are delivered to the owner's error callback.

The reviewed runner restores up to 4096 bytes of application state through the existing paid command channel. Private v3 journal capacity and public quota v2 remove the earlier 512-record/count obstacle when explicitly selected, but do not increase that per-restore application-state limit. Cadence captures application state, not a VM snapshot. Remote provider approval, real independent host failover, sealed CPU capacity and funded public Base acceptance remain separate release gates.

## Validation boundary

`tests/paid-lifeline-reservations.test.ts` verifies concurrent polls, conservative cumulative ceilings, actual encrypted private-journal reopen after ambiguous broadcast, admission-response loss, stale/kill/expiry fencing, explicit operator quota wiring, retained stale-reservation inventory and mixed-age owner/wallet recovery rejection. Its compute/wallet ports are controlled test doubles. These are owner-adapter safety tests, not evidence of a public wallet transaction or a day of live operation. Actual paid backend lifecycle and M8 acceptance are reported separately with their source cutoffs.
