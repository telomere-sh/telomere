# Bounded paid application lifecycle runner

`PaidAgentLifecycleRunner` executes one owner-approved `migrate` or `rollover` intent in **full CPU mode** between two separately funded, admitted Platform Agent Vault sessions. It implements the existing `ClientAgentRunner` used by `ClientAgentCoordinator`; the Cyst recovery and vault master keys stay owner-side. The approved non-sealed controller and HostKit receive application plaintext through the command protocol. The runner does not quote, fund, admit, sign or broadcast a transaction. The owner supplies an external, idempotent stop-wallet port and a read-only chain client.

The source and target must have different registered HostKit identities, the same reviewed image digest, the same original owner, agent wallet, Vault and Leash, and leases of at most 120 seconds. The target is approved and on-chain open when the intent is planned. Platform runtime serializes paid sessions, so the target can be **queued without a HostKit lease** during checkpoint and stop. After source cleanup, a subsequent runtime drain starts that original target; `attach` waits for its signed lease. A queued target is never treated as an existing Cell. If its reservation or lease expires before attach or restore, the transition remains pending for owner reconciliation. The runner cannot silently fund or substitute another run.

The fixed checkpoint executable receives `sourceRunId, operationId` and must implement the [paid checkpoint contract](paid-session-checkpoint.md). The fixed restore executable receives `sourceRunId, targetRunId, intentId, checkpointId, operationId, stateSha256`. Its stdin is JSON containing those fields, `protocol: "telomere-paid-lifecycle-restore-v1"` and canonical `stateBase64`; stdout must be the same object without `stateBase64`. It must durably apply or recover exactly that operation, then return the exact receipt. Both executables are fixed before the lifecycle starts; they run only inside the already approved paid image. The 4,096-byte application-state limit fits the existing 8 KiB command stdin. It migrates application bytes, not a process, memory snapshot or GPU state. No confidential key release or TEE proof is provided; Cyst recovery keys are never part of the state/command protocol. Plaintext reaches the reviewed host/controller command journal.

The owner uses one `CystCheckpointFileVault` with a retained 32-byte master key and wraps it in `PaidLifecycleClientVault`. This adapter supplies the existing coordinator's checkpoint/key contract and stores immutable encrypted records for each original intent's pair, stop submission, confirmed stop transaction, target lease, attach and restore. A later separately approved lifecycle intent can use the same owner vault without replacing the earlier records. The same vault directory and key must be reopened after a daemon crash. The owner keeps its original lifecycle intent ID and Cyst recovery material; a new Vault, scope, image, operation or pair fails before a guest command. A captured checkpoint is reused after a lost Cyst response, while the HostKit command ID and reviewed guest hook make lost checkpoint/restore responses retry the exact original command.

The external stop port has `submit(plan, operationId)` and durable `lookup(operationId)` methods. The runner persists a submission marker *before* calling it. If the response is lost, the runner looks up that same operation; an absent hash is ambiguous and it refuses to submit another transaction. The local acceptance reopens the owner vault while retaining the test wallet port's lookup map; a production wallet port must persist that lookup independently if its process can restart. The returned transaction must be canonical, successful, sent by the human owner to the original Vault on the reviewed chain with the exact owner stop plan and zero value. The canonical receipt must contain the escrow's `StopRequested` event for the original source; the on-chain run at that block must retain the original Vault payer/host and stop time. `attach` and `resume` reverify this proof, so a later reorg cannot turn a saved hash into permission to restore.

After stop, the controller's paid-session API must report `receipt_pending` or later with a terminal outcome, persisted HostKit cleanup and an event history ending in `session_exit`. Its `terminalSession` path checks that durable history, session outcome and receipt hash agree. This is **controller/HostKit runtime acceptance of physical cleanup**, not an independent remote attestation of a host tick. The runner revalidates the live intent immediately before checkpoint and restore command dispatch; owner kill in the final cross-service interval before a command cannot be made atomic by this adapter, so the reviewed guest hook must also bind and fence its operation. Final financial settlement and Vault burn can occur later; the source's reservation stays outstanding until the normal receipt-root publication, canonical settlement and Vault sync. This ordinary owner lifecycle flow does not change `PaidPreemptionHandoff`, which still requires canonical source settlement before target restoration.

The caller must create the approved original pair and intent, construct `PaidAgentLifecycleRunner` with authenticated `PlatformVaultRuntimeClient` reads/commands plus owner-only `stopPlan`, then pass the **same** `PaidLifecycleClientVault` to `ClientAgentCoordinator`. Call `step` until the source stops; start the queued target through the existing runtime drain and continue `step`/`finish` while its lease is live. Keep the external stop-port lookup and vault master key across restarts. The local integration test uses real Anvil contracts, two distinct HostKit identities with local-process fixture backends, authenticated HTTP clients, Cyst encryption, lost stop and restore responses, disk vault reopen, two separately approved hops of one application, application counter continuation, and fee-inclusive conservation for all three original reservations. It does not establish production gVisor/Kata execution or a public-network wallet transaction.
