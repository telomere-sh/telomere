# Private Cyst backup and restore

Application Cysts are encrypted by the client with XChaCha20-Poly1305. The controller stores immutable ciphertext files and PostgreSQL metadata. A complete Cyst recovery needs both stores and the client's recovery key. The operator never receives that key or checkpoint plaintext.

The private staging backup still includes its existing generated operator keys in `profile.env`, along with its database and local-chain state. Keep the entire backup private and outside Git. The additional Cyst snapshot contains only opaque ciphertext, file lengths and SHA-256 digests; it adds no client recovery keys or plaintext.

## Backward compatibility

| Profile | Manifest | Required files |
| --- | --- | --- |
| `CYSTS_ENABLED` absent or `false` | Version 1 | `database.dump`, `chain.json`, `profile.env` |
| `CYSTS_ENABLED=true`, explicit `CYSTS_DIR` | Version 2 | The same three files plus `cysts.snapshot.json` |

Historical version 1 backups retain their three-file checks and do not require Cyst tables or a ciphertext directory. An enabled profile cannot be verified with a version 1 manifest. A version 2 manifest cannot silently downgrade to a disabled profile.

The staging profile uses an explicit private directory:

```dotenv
CYSTS_ENABLED=true
CYSTS_DIR=/opt/telomere-pilot/data/cysts
```

## Consistent capture

`npm run backup:staging` requires both dedicated staging services, `telomere-staging.service` and `telomere-staging-chain.service`, to be cleanly inactive. All managed CPU cells must be absent. The command checks these conditions before and after capture and does not start services.

Under this pause, the command captures the PostgreSQL archive, local chain, profile and Cyst files. It also reads Cyst references in a PostgreSQL read-only transaction. Every `ready` row must have its exact tenant-derived ciphertext file with the expected SHA-256 and length before the snapshot is written and the backup is finalized. A `pending` row may have no file; its durable quota and upload identity remain in the database archive.

Only flat filenames of the form `<64 lowercase hex characters>.blob` are captured. They are generated by `PrivateCystStorage` from the normalized owner and ciphertext digest. Unknown files, directories, symlinks, hard links, public POSIX permissions and interrupted `.tmp-<UUID>` uploads cause capture to fail. Inspect such files while the controller remains stopped; the backup command neither deletes them nor includes them.

A failed capture leaves a private partial backup directory for inspection. It does not produce a successful manifest. If services accidentally start during capture, preserve the partial capture and take a new backup after a clean pause.

## Snapshot format and bounds

`cysts.snapshot.json` is a strict version 1 JSON document with a fixed kind, total ciphertext byte count and sorted, unique blob entries. Each entry contains exactly `name`, `bytes`, `sha256` and canonical base64 `ciphertext`. The enclosing version 2 backup manifest checksums this complete file and records its blob count and total ciphertext size. There is no tar/zip extraction or request-supplied output path.

Operational bounds are:

- 4,096 ciphertext files per snapshot.
- 128 MiB total ciphertext and 192 MiB maximum encoded snapshot file.
- 17 through 2,097,168 bytes per blob, matching the Cyst payload limit.
- 65,536 metadata references or owner records in a backup/restore exercise.

These are backup limits in addition to the application's per-owner quotas. Exceeding them fails capture or verification; it does not truncate the data. Restore validates the snapshot before creating its destination. Capture checks source names and sizes before writing the ciphertext snapshot. Other files in a partial backup may already have been captured and remain private.

Verification checks the outer manifest checksum, canonical encoding, individual ciphertext digests, lengths, total count and private file layout. Checksums detect corruption; only client decryption with the original recovery key authenticates encrypted application content and its associated metadata.

Reads pin an `O_NOFOLLOW` descriptor after file preflight. Snapshot reads allocate only the checked file size and probe at most one extra EOF byte. Streamed hashes have the same declared byte bound. Before accepting bytes, verification checks the descriptor and original pathname with exact device/inode identity, single link, permissions, size and modification/change timestamps. Concurrent growth, truncation, replacement or added links fail verification rather than increasing the allocation or silently changing the hashed source.

## Isolated restore acceptance

```sh
npm run restore:acceptance -- --directory /opt/telomere-pilot/backups/<verified-backup>
```

The exercise restores the matching PostgreSQL archive into an empty, uniquely labelled scratch container and loads a private copy of the corresponding Anvil state. For an enabled backup it restores ciphertext to a newly created private directory under that exercise and overrides `CYSTS_DIR` only in the scratch configuration. Existing or symlinked destinations are refused. No live Cyst file is overwritten, and the original staging profile is unchanged.

The restored database schema includes `cysts` and `cyst_owners`. A read-only acceptance transaction checks all checkpoint metadata against the snapshot, owner quota totals and `CystService.download` hashes and lengths for ready rows. Owners with only ready rows also receive a paginated `CystService.list` check. For owners with pending rows, acceptance validates their raw metadata and reads pending ciphertext directly through `PrivateCystStorage`; it deliberately defers `list`, because that application path now repairs completed pending uploads and writes the database. The report distinguishes verified list owners, deferred pending owners, recoverable pending blobs and pending rows with no blob. Ready checkpoints with missing or mismatched blobs fail, and pending states remain unchanged during acceptance. After normal recovery, a pending row with its complete immutable blob can become ready through the existing owner access path. A pending row without a blob needs a retry of its original encrypted upload and idempotency key, preserving the existing quota reservation.

The default acceptance profile retains the 512 checkpoints and 32 MiB limits per owner. An operator who explicitly enabled quota version 2 must retain the independent private policy file referenced by both `CYSTS_QUOTA_POLICY_PATH` and `CYSTS_QUOTA_POLICY_SHA256`. Restore acceptance reads that file through the same bounded, hash-pinned policy reader as controller startup. Only the exact supported 4,096-checkpoint policy is accepted; the byte limit remains 32 MiB. Missing pins, unavailable or modified files, and unsupported policy fields fail closed. A restored owner above 512 checkpoints cannot pass under the legacy profile, including an owner whose pending rows defer the list check.

`verifyRestoredCysts` receives this validated policy explicitly and selects the corresponding list profile. It initializes the scratch filesystem guard without calling `CystService.initialize`, so it never executes quota migration DDL in the read-only verification transaction. The archive must already contain its original quota schema. `backup:platform` and `restore:platform:verify` use the same external policy pins when checking paid small-checkpoint replica accounting. Their existing manifest formats and legacy limits remain unchanged; neither verifier enables a policy or repairs a remote replica.

The existing accepted signed receipt, canonical settlement event, transaction journal and balance conservation are checked in the same scratch database. The exercise starts no controller, CPU work or NEAR inference, and sends no transactions. It closes its database connection, stops its own Anvil process and removes only its exact labelled scratch PostgreSQL container. Private restored ciphertext and the acceptance report remain in the exercise directory for inspection.

## Local checks

`tests/cyst-backup.test.ts` exercises version 1 compatibility, enabled version 2 capture, relocation into a fresh PGlite metadata store, actual client ciphertext decryption, interrupted uploads, a real read-only transaction containing both recoverable and missing pending rows, tenant/digest bindings, malformed snapshots, bounds, symlinks, hard links and refusal to overwrite existing storage. Descriptor instrumentation places real appends and path replacement after checked stats to confirm bounded reads and rejection before success. Its `PGDMP` fixture checks backup format verification; the Linux restore acceptance command supplies the actual PostgreSQL archive restore check. `tests/operator.test.ts` retains the original backup/profile compatibility checks.

Quota-profile regression coverage restores 513 real encrypted checkpoints, verifies paginated reads and client decryption under the explicit v2 policy, and checks unchanged database constraints, metadata, usage and pending states. Missing or malformed policy fails before accepting expanded usage. `tests/platform-backup-quota-v2.test.ts` checks 513 encrypted metadata records against two local HTTP replica fixtures inside a real read-only PGlite transaction: all 1,026 successful object reads use GET, and corrupt replica bytes fail verification without a repair request. These fixtures test the verification path; deployed PostgreSQL archive and remote-storage recovery remain separate acceptance exercises.
